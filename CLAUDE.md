# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

SAVIOUR (Synchronised Audio Video Input Output Recorder) is a modular, PoE-networked multi-sensor recording system for rodent behavioural research. Each Raspberry Pi 5 on the network runs either as the **controller** or as a **module** (camera, microphone, TTL, RFID, etc.).

## Commands

### Python backend

```bash
# Activate the virtual environment first
source env/bin/activate

# Run tests — testpaths already covers src/controller/tests, src/modules/tests,
# and src/tests, so plain `pytest` runs everything:
pytest
pytest src/controller/tests/test_facade.py   # single file

# Lint — ruff is a dev dependency (pip install -e ".[dev]") and is what CI runs
ruff check src/

# Type check (aspirational — strict mypy config has never passed)
mypy src/
```

Note: `ruff check src/` has a large pre-existing baseline (~2000+ findings, mostly `PL*`) on `main` — CI clearly isn't gating on the full set. Keep new code clean of `E,F,B,UP,W,I,N` at least.

### Frontend (React/Vite)

```bash
cd src/controller/frontend
npm run dev          # dev server (proxies /socket.io to Flask on port 5000)
npm run dev:mock     # run the UI with an in-memory fake socket, no controller needed
npm run build        # production build → dist/
npm run lint
```

**After making any frontend change, run `npm run build`** so the user can review the result (they don't run a dev server themselves). If it fails with `EACCES`/`unlink` errors under `dist/`, that's the known root-owned-`dist/` issue — `sudo chown -R $(whoami) src/controller/frontend/dist` then rebuild, rather than deleting `dist/` outright.

## Architecture

### Two-role system

Every device runs one of two roles, set in `/etc/saviour/config`:

- **Controller** (`src/controller/`) — PTP grandmaster, mDNS service discovery, ZeroMQ command hub, Flask+SocketIO web interface on port 5000, recording session orchestration, file export queue to Samba/NAS.
- **Module** (`src/modules/`) — PTP slave, registers via Zeroconf, connects to the controller's ZeroMQ sockets, records to `/var/lib/saviour/recordings`, exports files to the controller's Samba share.

Concrete implementations live under `src/controller/variants/` and `src/modules/variants/`. Each subclasses the abstract `Controller` or `Module` base class.

### Inter-service communication

ZeroMQ **ROUTER/DEALER** for controller→module commands; modules publish status/heartbeats on PUB/SUB:

- Controller binds a ROUTER socket (port 5555); each module connects a DEALER socket with its `module_id` as the ZMQ identity and sends a `"hello"` frame on connect to register. Tracked in `_connected_dealers`; heartbeat timeout evicts a module via `remove_dealer()`.
- Modules publish on `status/<module_id>` (PUB, port 5556); controller SUBs to all topics.
- **Actual wire format**: commands are plain strings `"{command} {json_params}"` routed by identity; status messages are JSON dicts with `type`, `timestamp`, `module_id`, `module_name` plus type-specific fields. No envelope, no `msg_id`, no ack correlation.
- ⚠ `docs/PROTOCOL_V1.md` is **aspirational, not descriptive** — it documents PUB/SUB `cmd/` topics and a `msg_id`/ack/retry envelope that were never implemented. Do not use it as a reference for the current protocol.

### Config layering

JSON config is merged in three layers: `base_config.json` → `active_config.json` → `.env` overrides. Keys prefixed with `_` are internal defaults not meant to be user-overridden. The `Config` class in `config.py` handles this for both sides.

### Module command system

Module methods decorated with `@command()` are auto-registered as remotely callable RPCs. `@check()` registers status/health reporters. Commands are dispatched by the `Communication` class when a matching message arrives.

### Frontend↔backend

The React frontend communicates with Flask exclusively via **Socket.IO** (not REST). The Flask server emits module state, health, and recording events; the frontend sends commands back as Socket.IO events. The Vite dev server proxies `/socket.io` to `localhost:5000`.

The frontend variant (basic / loom / apa / habitat / acoustic_startle) is selected at build time via the `VITE_VARIANT` env var, which `saviour-config`'s `build_frontend()` writes; `vite.config.js` resolves the `virtual:active-app` alias to `src/${variant}/App.jsx`. Switching rigs means re-running the build with a different `VITE_VARIANT`, not editing source. `basic` doubles as the shared component library — `apa`/`habitat` `App.jsx` import pages straight from `../basic/`.

## Conventions

- **Conventional commits** with `feat/`, `fix/`, `refactor/` branch prefixes. Branch flow: PRs → `staging` → `main`.
- Python line length: 88 (ruff). Code requires **3.11+** (`match`, `StrEnum`, numpy ≥ 2.2) despite pyproject claiming py38; all deployed Pis run Bookworm/3.11+.
- Systemd-aware logging: timestamps are skipped when `INVOCATION_ID` is set (systemd sets this).
- PTP log parsing in `src/*/ptp.py`; health metrics in `src/*/health.py`.
- `src/__version__.py` is written by a **pre-commit hook** (`git describe`) so ZIP deploys carry the version — inherently one commit behind; never "fix" this with a manual bump. Hook is tracked at `scripts/git-hooks/pre-commit`; each clone must run `git config core.hooksPath scripts/git-hooks` once. If the version goes stale again, check `core.hooksPath` is set on whatever machine is committing.

## Project status & threat model

Currently **v0.6**, targeting **v1.0 = "safe to run unattended on a closed lab LAN without silent data loss or easy compromise"** — not "hardened for internet exposure". v1.0 deliberately excludes the big structural refactors (`web.py` blueprint split, Samba→rsync, module god-object composition refactor).

**Threat model (settled 2026-08-25):** the system treats **LAN access as the trust boundary** — anyone who can reach the network is treated as authorized, the same way SSH/physical console access to any of these Pis already is. The web UI's guest/admin split exists to stop an operator *accidentally* breaking a running experiment or leaking data (wrong button, mid-session config change), **not** to defend against a malicious LAN-resident actor. On that basis, `update_saviour` package-signature verification and the ZMQ identity-hijack path are **deliberately deferred** — both need nothing more than LAN access, which is already accepted as trusted. A credential committed to git history is compromised regardless of network exposure — that half is treated separately and the known hardcoded Samba passwords were fixed independently.

**Still open for v1.0:** wire the existing `python-app.yml` CI job (ruff + pytest, runs on push/PR to `main`) up as a *required* status check before tagging.

Completed work is archived with full write-ups in **[docs/CHANGELOG.md](docs/CHANGELOG.md)** — new completed items get a full write-up here first, then move there in a future condensing pass.

## Open work

### Correctness / data loss

- **`pyproject.toml`: `hatchling` in build-requires breaks offline module installs** — build backend is `setuptools.build_meta` so hatchling is never used, but pip's build isolation tries to download it (+ setuptools/setuptools_scm) on every `pip install -e .`. This is the `ERROR: No matching distribution found for hatchling` in module journals. Fix: remove hatchling from requires AND use `--no-build-isolation` in mend.sh/update paths; delete the dead `[tool.hatch.*]` sections.
- **`recording.py`: `delete_session()`/`clear_ended_sessions()` block on `total_exports_failed > 0` forever**, even once every file has genuinely reached the share — it's a lifetime counter, never decremented. Open design call: whether it alone should keep blocking a plain delete once `pending_exports` is back to 0. `force=True` still available.
- **`camera_base.py`: recorded video rotation silently dropped for non-square resolutions at 90°/270°** — genuine hardware limit (the ISP can't do a true transpose on this platform; the recorded "main" stream is a fixed-shape DMA buffer the HW `H264Encoder` reads directly). Live preview rotates correctly; recording doesn't. **Partial fix 2026-08-14**: the baked-in timestamp overlay is now pre-rotated (`_apply_timestamp` `compensate_k`). **Scope decision 2026-08-25**: don't rewrite the encoder path — push visual rotation downstream instead (a frontend CSS/video transform driven by the stored `camera.rotation`, or an `ffmpeg -vf transpose` post-pass in `video_compose.py` / the download path). **Not yet implemented** — nothing downstream reads `camera.rotation` today; this is new work.
- **Nothing verifies a module's recording pipeline is still producing data — `is_recording` is a write-once flag, not a liveness signal.** `Health.get_health()`'s `recording` field is set `True` once at start and cleared only by a successful `stop_recording()`. `camera_base.py`'s `_frame_precallback` and the microphone's per-device thread both catch every exception with log-and-continue, so a wedged-but-not-crashed pipeline is invisible end-to-end (the controller's `_monitor_sessions()` reads the same boolean). Needs a per-pipeline liveness signal (last-frame-written timestamp vs expected fps).
- **`recording.py` (module-side): the critical-low-disk auto-stop reports identically to an operator stop, and only checks once per segment boundary** — with 60-min segments a disk that fills mid-segment isn't caught until the next boundary; when it fires, `stop_recording()` takes the same success path as a manual stop, so the controller can't distinguish "operator stopped" from "module force-stopped to protect the filesystem". Needs a distinct reason field + moving the check outside the segment-boundary gate.
- **`recording.py`: legacy string command path can crash `start_recording`** — `duration > 0` compares a string to `int` when duration arrives via the non-JSON `"start_recording duration=60"` path → uncaught `TypeError` surfacing as an opaque ack.
- **`web.py:400`: broken timestamp format in the legacy `send_command start_recording` path** — `strftime("%Y%M%d_%H%m%s")` has month/minute swapped and non-portable `%s`; should be `"%Y%m%d_%H%M%S"`.
- **`modules/network.py` / `module.py`: module-side network-ready wait has no timeout** — `_find_own_ip()` and `_wait_for_network_ready()` loop forever on `nmcli`/`hostname -I`; the exact bug already fixed controller-side but never ported.
- **`ptp.py`: `_monitor()` exits permanently on the first transient PTP hiccup** — no retry/restart if `ptp4l`/`phc2sys` transiently reports non-active; the controller's PTP status thread can die quietly and never recover without a service restart.

### Security (open)

Threat model context above — the deferred items are a deliberate decision, not an oversight.

- **Deferred for v1.0:** `update_saviour` / `deploy_update` package signature/checksum verification (currently only `zipfile.is_zipfile()`); ZMQ `ROUTER_HANDOVER` identity-hijack (a spoofed `module_id` silently steals another module's command stream); `/update/package` staying unauthenticated (modules fetch it with no admin password available). ZMQ CURVE auth/encryption, web UI TLS, Samba SMB3 sealing, fleet SSH-key/password rotation on clone — all framed as "closed-LAN only" caveats, v1.0 ships with that stated.
- **Web UI: single shared password, plaintext, no lockout** — Flask-SocketIO over plain HTTP, so the admin password is sniffable on every login/reconnect. `authStorage.js` caches it in `localStorage` indefinitely. `handle_login` has no rate-limiting/lockout and never logs failed attempts. `cors_allowed_origins="*"` widens this.
- **No transport encryption on the Samba/CIFS export** — mount commands never set the SMB3 `seal` option; recorded data and briefly-`ps`-visible mount credentials cross the LAN in plaintext.
- **All network services bind `0.0.0.0` with no interface scoping** — if the controller ever doubles as the internet gateway, the unauthenticated command bus and sniffable-password web UI become WAN-reachable. No firewall rule scopes anything to `eth0`.
- **Fleet image cloning never rotates the OS user's password / `~/.ssh/authorized_keys`** — `multiclone.sh`/`clone_prep.sh` regenerate SSH *host* keys + machine-id but never the login credential; whatever the master image's imager set is shared, unrotated, across every cloned device.
- **`push_credentials.sh` disables SSH host-key checking** (`StrictHostKeyChecking=no`) and passes the password as a literal SSH command-line arg (briefly `ps`-visible on the module).
- **`saviour.service` runs fully as root with no systemd hardening** — no `NoNewPrivileges`, `ProtectSystem`, capability bounding. Reasonable for `ptp4l`/`phc2sys` (raw clock hardware); not obviously necessary for the whole ZMQ/web/update surface.

### Architectural concerns

Larger structural issues requiring significant refactoring — recorded so they aren't lost.

- **Module base class is a god object** — `module.py` (~1275 lines) owns config, export, PTP, recording, health, network, commands, lifecycle. No concern testable in isolation. Needs a composition refactor across all module types.
- **`web.py` is a 2000-line grab-bag** — sessions, config sync, chunked update uploads, deployments, bug-report collection, NAS probing (3 duplicated mount/umount snippets), time setting, power control, all in two giant registration methods. Split into Flask blueprints.
- **Unsupervised threading + broad exception policy** — 59 ad-hoc `threading.Thread(daemon=True)` spawns and ~280 `except Exception` handlers. A crashed monitor/retry thread dies silently. Consider a tiny supervised-thread helper (log-and-restart) for the long-lived loops.
- **`modules/communication.py`: heartbeat-watchdog force-reconnect crashed the whole process with a fatal libzmq assertion, mid-recording** (found live 2026-08-20 on `habitat_camera`) — `2 consecutive heartbeat acks missed → _force_reconnect() → cleanup() closes the command socket → Assertion failed: pfd.revents & POLLIN (src/signaler.cpp:238) → SIGABRT`. Fatal C-level assertion, uncatchable. Likely cause: `cleanup()` (spawned in its own thread by the ack watchdog) tears down `command_socket`/`context` while `listen_for_commands()`'s listener thread may still be blocked inside a receive on the same socket. Also: `_schedule_reconnection()`/`_attempt_reconnection()` (the independent "Connection refused" reconnect path) does **not** acquire `_reconnect_lock` — an unguarded concurrency gap regardless of whether it's the trigger here. systemd auto-recovers within ~10s, so this is a rough restart not silent data loss. Next step: make `_schedule_reconnection`/`_attempt_reconnection` share `_reconnect_lock` with `_force_reconnect`, then look at whether `listen_for_commands()` needs to signal "returned from recv, not about to re-enter" before `cleanup()` proceeds past the socket close.
- **Controller/module/frontend "variant" selection is hardcoded and conflates three axes of change** — a single `DEVICE_TYPE` string drives `get_python_path()`'s `variants/${DEVICE_TYPE}/${DEVICE_TYPE}_controller.py` convention *and* `build_frontend()`'s `VITE_VARIANT`, forcing a 1:1 pairing between "new frontend variant" and "new controller Python class" even when the variant needs zero backend logic (`loom_controller.py` is a pure no-op subclass). **Shipped so far:** `examples/` → `variants/` rename (2026-08-13); menu auto-detection from `*/variant.conf` `NAME`/`DESCRIPTION` (2026-08-17); `variant.conf` carries `FRONTEND` + module `APT_PACKAGES`. **Proposed full fix:** extend `variant.conf` with `ENTRYPOINT`/`CONFIG_FILE`; make the unit file *invariant* (one fixed `ExecStart=... src/main.py` launcher that reads `DEVICE_TYPE`/`DEVICE_ROLE` and dynamically imports the entrypoint). **Blocking prerequisites (open):** (1) fixed launcher + dynamic dispatch; (2) `__file__`-relative config loads (`load_controller_config()` uses CWD-relative `os.path.abspath()`, only works because `WorkingDirectory` is per-variant today); (3) invariant `configure_service()` — `update_saviour()` never regenerates the unit file, so a path-moving code push leaves a deployed device's unit file stale and the service down. Stopgap shipped: `saviour-config --regenerate-service`, called by `mend.sh` step 7 every run. **Don't** move the frontend into `variants/<slug>/frontend/` — `basic` is the de facto shared component library. Smaller cleanup worth doing first: extract genuinely-shared `basic/{components,pages}` into `src/controller/frontend/src/shared/`.
- **Samba is the wrong export transport** — designed for Windows interop; adds credential management, mount failure modes, an unreliable driver stack on a homogenous Linux PoE network. `rsync` over SSH or an HTTP PUT endpoint would be simpler. High effort — rewrites all export logic.
- **NWB export** (scoped 2026-08-13, `docs/NWB_EXPORT_DESIGN.md`, not implemented) — a standalone post-hoc `tools/export_nwb.py` reading an exported session dir. Surfaces two pre-existing gaps worth fixing regardless: no `species` field in `experiment_metadata`, and `RecordingSession.start_time`/`end_time` are naive local time rather than timezone-aware (`session_metadata.json`'s `created_at` already does this right).
- **Habitat deployment improvements — UI + reliability at 20-module scale** (scoped 2026-08-21, `docs/HABITAT_SCALE_IMPROVEMENTS.md`, not implemented) — five separable proposals: configurable livestream grid dimensions + cell aspect ratio (both currently hardcoded 4×4 and force-cropped to 1:1); bulk module actions on `System.jsx`; fleet health rollup on the Dashboard; disk/export-backlog trend view; reliability items reprioritized for scale.

## Hardware gotchas

### AudioMoth USB microphone

- **Device name encodes sample rate.** The AudioMoth firmware names its USB audio device after its current sample rate (e.g. `250kHz AudioMoth USB Microphone`). Calling `configure_audiomoth()` to change the rate causes PulseAudio/PipeWire to drop the old device ID and register a new one. Any code that stores a PulseAudio device ID (e.g. `self.audiomoths`) must re-discover after reconfiguration — otherwise `soundcard.get_microphone(id)` raises `IndexError` intermittently while the monitoring stream (opened at startup) keeps working on the stale stream.
- **Effective bandwidth is much lower than Nyquist at low sample rates.** The EFM32's PDM decimation filter provides only a fraction of the theoretical bandwidth: ~5 kHz usable at 48 kHz, ~20 kHz at 96 kHz, ~70 kHz+ at 192 kHz. 192 kHz is the only rate suitable for ultrasonic rodent vocalisation work. Do not assume Nyquist = usable bandwidth.
- **Monitoring and recording use separate soundcard recorders** on the same physical device. PipeWire supports multiple simultaneous readers, so this is intentional and works correctly.

### Controller clock (PTP grandmaster)

- The controller runs `phc2sys` to discipline the system clock from its PTP hardware clock. This means `systemd-timesyncd` / NTP is active and `timedatectl set-time` will fail with *"Automatic time synchronization is enabled"*. Any code that sets the system time must disable NTP first (`timedatectl set-ntp false`), set the time, then re-enable it (`timedatectl set-ntp true`) — ideally in a try/finally.

### Hailo AI HAT / PCIe driver (`apa_camera`, `lightning_camera`)

- **`hailort-pcie-driver` needs `dkms` installed *before* it does, or it silently falls back to an unmanaged one-off kernel module build that breaks again on the next kernel upgrade** (found 2026-08-18). If `dkms` isn't present, the postinst prints `Failed to install PCIe driver to the DKMS tree. Trying to install PCIe driver without DKMS` and builds a plain module for the *currently running* kernel only — nothing rebuilds it on the next `apt upgrade`, so `modprobe hailo_pci` then fails with `Module hailo_pci not found`. Fixed for new installs by ordering `dkms` ahead of `hailo-all` in both variants' `variant.conf` `APT_PACKAGES` (the loop installs one at a time in list order). Already-provisioned Pi in this state: `sudo apt install dkms && sudo apt install --reinstall hailort-pcie-driver && sudo reboot`.
- **Diagnostic order for "Hailo device not found"**: `lspci | grep -i hailo` first (is the PCIe link up? if not, check `dtparam=pciex1`/`dtparam=pciex1_gen=3` in `/boot/firmware/config.txt`, reboot after adding) → `lsmod | grep hailo` → `dmesg | grep -i hailo` → `dkms status` (built against the running kernel per `uname -r`?).
- **Hailo-8 vs Hailo-8L**: `lspci | grep -i hailo` names the actual chip. `tools/convert_to_hailo.py`'s `--hw-arch` defaults to `hailo8l` but some devices carry the full Hailo-8 (26 TOPS vs 13). Note `lspci` sometimes says generic "Hailo-8" for a real 8L — confirm via `hailortcli fw-control identify` (`.arch`).

### Pi 5 PoE power delivery (NVMe controllers + PoE HAT modules)

Every device is a Pi 5 powered over PoE — controllers via the 52Pi EP-0240 M.2 NVMe M-Key PoE+ HAT, most modules via the Waveshare "PoE HAT (F)".

- **NVMe autonomous power-state transitions (APST) can wedge the whole device, requiring a manual power cycle** (found 2026-08-25, live on a habitat controller booting from a Kingston SKC3000S512G). Diagnosed from `journalctl -b -1 -k`: bursts of `nvme nvme0: I/O tag ... timeout, aborting req_op:WRITE`; the first two recovered, the third did not — journal goes silent for ~5 h until a manual power cycle (root filesystem hung). Not undervoltage (`vcgencmd get_throttled` was `0x0` the whole boot). Cause: the kernel default `nvme_core.default_ps_max_latency_us` (100 ms) lets the drive drop into a deep power-saving state it can fail to wake from.
  - **Fix**: append `nvme_core.default_ps_max_latency_us=0` to `/boot/firmware/cmdline.txt` and reboot. Applied automatically by `setup.sh`'s `configure_nvme_power_management()` (fresh) and `mend.sh` step 7/9 (deployed), both idempotent, both printing a reboot reminder. NVMe-specific, so controllers only. `multiclone.sh` clones inherit it (it only patches the PARTUUID) as long as the master image has had `setup.sh`/`mend.sh` run since this landed.
- **`PSU_MAX_CURRENT` (bootloader EEPROM) was found completely unset on the same controller** — the Pi 5 bootloader learns a high-amp supply via USB-C PD, which never happens over a GPIO-header PoE HAT, so it defaults to a conservative 3A budget instead of the ~4.5A both HATs can deliver. Both vendors document `PSU_MAX_CURRENT=5000` as a required step. Plausibly a contributing factor to the hang above.
  - **Fix**: `sudo rpi-eeprom-config --apply <config-with-PSU_MAX_CURRENT=5000>`, reboot. Applied automatically **fleet-wide** (not NVMe-gated) by `setup.sh`'s `configure_psu_max_current()` and `mend.sh` step 8/9, both idempotent.
  - **Caveat**: `rpi-eeprom-config --apply <file>` defaults to bundling the *latest available* bootloader firmware release when the file doesn't pin a `.bin` — so applying just this one line can also silently bump the bootloader firmware (same stable channel). Harmless in practice.
  - Like the NVMe fix, `rpi-eeprom-config` reads the *currently running* config — it won't self-report `[OK]` until after the reboot.
- **Module-side reboots have now been seen too** (found 2026-08-27, habitat session `CRLLT3-247Cameras-camera-173650`) — 5 of 16 camera modules each did one unexplained full OS reboot over 19 h (`health.json` `uptime` reset, segment counter restarted). The 2 h journal retention was too short to catch the cause. A `Waveshare PoE HAT (F)` module browning out under sustained encode + hourly concurrent-export load is exactly the `PSU_MAX_CURRENT`-unset scenario — rule it in/out first on the affected Pis (`camera_34ec`, `camera_a2d2`, `camera_d549`, `camera_d586`, `camera_98b7`).
- **Each recording session now exports its own journal snapshot** (2026-08-27, `fix/habitat-session-followups`) — `Recording.stop_recording()` writes `<session>_<module>_journal_(<ts>).txt` (saviour.service + kernel, `--since` the recording start) into `to_export/`, so it rides the normal export to the share next to the footage. Best-effort; toggle with `recording.export_session_journal` (default on).
- **Export Diagnostics bundle now includes previous-boot + kernel journals** (2026-08-27) — was `journalctl -u saviour.service -n 500` per side (current boot, unit only, no kernel), structurally blind to a reboot cause. Now each module returns: `logs.txt` (current boot, 3000 lines), `logs_prevboot.txt` (`-b -1`), `kernel_prevboot.txt` (`-k -b -1`), `boots.txt` (`--list-boots`); the controller adds `kernel.txt`. Depends on persistent journald actually being on.
- **Persistent journald was OFF on a deployed module despite being in `setup.sh` + `mend.sh` since 2026-06-29** (found 2026-08-27 on `camera-module-34ec`: `journalctl -b -1` → "no persistent journal was found") — almost certainly cloned from a master SD image predating that commit and never re-mended (`multiclone.sh` doesn't run `setup.sh`/`mend.sh`). Fix fleet-wide: `run_mend` (or `sudo bash mend.sh`) on every module, then confirm `journalctl --list-boots` lists more than one boot. Do this **before** chasing the 5 module reboots — without it the next occurrence is just as blind.
- **`mend.sh` reboot marker: `/run/reboot-required`** — written (with a one-line `saviour mend: ...` reason) whenever step 7 (NVMe APST) or step 8 (`PSU_MAX_CURRENT`) *actually changed* something, and `mend.sh` exits `10` instead of `0`. Deliberately the same path Debian's `update-notifier` uses; `/run` is tmpfs so it self-clears on the reboot. `mend.sh --reboot` (opt-in, default off) reboots at the end iff the marker was written; `run_mend(reboot=True)` passes that through and its reply is `{"result": "reboot_required"}` (still a success). Find mended-but-not-rebooted devices: `[ -f /run/reboot-required ]` across the fleet, or exit-10 in `/var/log/saviour-mend.log`.
- **Diagnostic checklist for "Pi went unreachable, needed a power cycle"** on any Pi 5 in this fleet: `journalctl --list-boots` (find the gap and the preceding boot) → `journalctl -b -1 -k -g nvme` (timeout bursts; NVMe only) → `vcgencmd get_throttled` (flagged undervoltage — a live/sticky-since-boot read, not historical) → `sudo rpi-eeprom-config | grep PSU_MAX_CURRENT` (missing/wrong = firmware may have been power-budget-limiting; `[ -f /run/reboot-required ]` = fix queued but not activated) → NVMe devices also: `cat /sys/class/nvme/nvme0/power/control` (`auto` = APST active) and `/sys/module/nvme_core/parameters/default_ps_max_latency_us` (100000 = default/unmitigated).

### Module offline detection

- Modules do **not** send a graceful mDNS goodbye on ungraceful disconnection (power loss, switch unplug). The heartbeat timeout (90 s, `HEARTBEAT_TIMEOUT_SECS` in `modules.py`) is the only mechanism for these. `last_heartbeat_time` must be non-zero before the timeout fires, so newly registered modules with no heartbeat yet are not immediately evicted.

### PTP network topology (multi-switch habitats)

The controller is the PTP grandmaster; every module disciplines its PHC from it. The fleet switches (habitat rigs: **TP-Link TL-SG1218MPE**, 16-port Gigabit PoE+ "Easy Smart") are **plain L2 — not IEEE 1588 transparent or boundary clocks**. That has two consequences `ptp4l` cannot correct for:

- **Every switch hop adds variable queuing (residence) delay** to PTP event messages. A non-PTP switch doesn't measure or subtract it, so it shows up as offset jitter that grows with hop count.
- **Bulk traffic on a shared link delays PTP packets** — a Samba export frame in flight makes the next Sync/Delay_Req wait behind it. `ExportQueue` caps this at `max_concurrent_exports`, but even 1–2 concurrent ~250 MB transfers across the trunk a module syncs over is enough to nudge a marginal slave over threshold.

**This is fixed by wiring, not code.** SAVIOUR must stay topology-agnostic — do not add QoS-tuning, VLAN-aware logic, or per-habitat network assumptions. The standard for any habitat, independent of module count:

1. **Grandmaster (controller) and the export share on the same switch.** That switch is the PTP root.
2. **No module more than 2 switch hops from the controller** (1 is ideal).
3. **No third switch in the PTP path.** With two habitat switches, link them *directly* — SFP-to-SFP — not via an aggregation switch.
4. If a building uplink is needed, hang it off **one** habitat switch as an edge port so grandmaster traffic never traverses it.
5. Beyond 2 switches per habitat, or if contention persists at 2 hops, the answer is **PTP transparent-clock switches**, not config.

**Found 2026-08-27** (habitat session `CRLLT3-247Cameras-camera-173650`): two TL-SG1218MPEs joined *via a third switch* gave far-side modules a 3-hop uncorrected path vs 1 hop for modules on the controller's switch, matching the clean-vs-marginal split (8 stable / 12 unstable, the 12 including all 4 microphones). Remedy: direct SFP link between the two switches, controller + share on one, middle switch demoted to edge-uplink-only. Confirm before/after by mapping module MAC → switch port (each switch's web GUI, Monitoring → MAC address table) against the controller's `ip neigh`, and a fresh `/api/ptp_history.csv` a day after. This was a *secondary* contributor — the primary cause of the hourly sync episodes was the `_check_ptp_health()` restart loop (branch `fix/ptp-auto-restart-feedback-loop`); re-measure after that lands before deciding how much the rewire still buys.

### Camera framesync (multi-camera timing)

The camera module supports `camera.sync_mode: "server" | "client" | "none"` — **libcamera's software sync**, not GPIO. The server broadcasts timing packets over UDP; clients adjust their framerate to match.

- **`SyncTimer` metadata**: counts down (µs) to the agreed sync point, then goes negative. A very negative value (e.g. −26 s) means sync was established long before recording started — not an error.
- **`SyncReady` metadata**: True on the single frame where sync fires. The encoder's `sync_enable = True` discards frames until this fires. `SyncFrames` is set in `_pre_create_first_segment()` to force a fresh sync point close to T=0. The per-frame timestamp CSV is opened in `_start_new_recording()` (not `_pre_create_first_segment()`) so CSV row 0 always corresponds to video frame 0.
- **Phase offset**: even after sync-lock, there's a fixed per-session inter-camera phase offset (typically 0–8333 µs at 120 fps). A hardware characteristic of when the client's frame clock happened to be when sync was established — **not** a PTP error. Constant within a session; calibrate out from the `framesync_per_frame.csv` sidecar.
- **120 fps limitation**: libcamera sync requires the target framerate to be significantly below the camera's max so the client can speed up to catch the server. At 120 fps on Pi Camera Module 3 the client has no headroom and cannot phase-lock. `sync_enable`/`SyncFrames` is still used best-effort with a 2 s fallback timeout.
- **PTP two-servo rule**: `ptp4l` disciplines the PHC; `phc2sys` disciplines `CLOCK_REALTIME`. The recording-**start** gate (`_check_ptp_sync` in `recording.py`, every start path) checks both `ptp4l_offset` and `phc2sys_offset` against **`recording.ptp_start_gate_us`** (default **50 µs**, its own key since 2026-08-28 — split off `ptp_threshold_us`, now only the looser mid-recording "degraded" *warning*, ~1 ms). Both keys are on Settings → Thresholds. `phc2sys_freq` (ppb) reflects the crystal's natural offset and is typically 20,000–30,000 ppb on settled hardware — **normal, don't gate on it**. What matters is the *difference* between cameras' freq values. Wait 5–10 min after a camera reboot before recording for phc2sys to converge.
- **Framesync analysis**: `tools/analyse_framesync.py` reads per-session timestamp CSVs and reports inter-camera offset stats including clock drift (µs/sec) and detrended jitter. Run with `source env2/bin/activate` (needs pandas). The "mean offset" includes the fixed phase offset; the **detrended p95** is the meaningful accuracy figure (<20 µs with settling PTP, <5 µs when fully converged).
