## Project Overview

SAVIOUR (Synchronised Audio Video Input Output Recorder) is a modular, PoE-networked multi-sensor recording system for rodent behavioural research. Each Raspberry Pi 5 on the network runs either as the **controller** or as a **module** (camera, microphone, TTL, RFID, etc.).

## Architecture

### Two-role system

Every device runs one of two roles, set in `/etc/saviour/config`:

- **Controller** (`src/controller/`) — PTP grandmaster, mDNS service discovery, ZeroMQ command hub, Flask+SocketIO web interface on port 5000, recording session orchestration, file export queue to Samba/NAS.
- **Module** (`src/modules/`) — PTP slave, registers via Zeroconf, connects to controller's ZeroMQ sockets, records to `/var/lib/saviour/recordings`, exports files to the controller's Samba share.

The concrete implementations live under `src/controller/variants/` and `src/modules/variants/` (renamed from `examples/` 2026-08-13 — see the Architectural concerns section below for what did and didn't come with that rename). Each variant subclasses the abstract `Controller` or `Module` base class.

### Inter-service communication

ZeroMQ **ROUTER/DEALER** is used for controller→module commands; modules publish status/heartbeats on a PUB/SUB socket:

- Controller binds a ROUTER socket (port 5555); each module connects a DEALER socket with its `module_id` as the ZMQ identity and sends a `"hello"` frame on connect to register.
- Controller tracks connected dealers in `_connected_dealers`; heartbeat timeout evicts a module and calls `remove_dealer()`.
- Modules publish status/heartbeats on `status/<module_id>` (PUB, port 5556); controller SUBs to all topics.
- **Actual wire format**: commands are plain strings `"{command} {json_params}"` routed to the DEALER by identity; status messages are JSON dicts with `type`, `timestamp`, `module_id`, `module_name` plus type-specific fields. There is no envelope, no `msg_id`, and no ack correlation.
- ⚠ `docs/PROTOCOL_V1.md` is **aspirational, not descriptive** — it documents PUB/SUB `cmd/` topics and a JSON envelope with `msg_id`/ack/retry semantics that were never implemented. Do not use it as a reference for the current protocol.

### Config layering

JSON config is merged in three layers: `base_config.json` → `active_config.json` → `.env` overrides. Keys prefixed with `_` are internal defaults not meant to be overridden by users. The `Config` class in `config.py` handles this for both controller and module sides.

### Module command system

Module methods decorated with `@command()` are auto-registered as remotely callable RPCs. `@check()` registers status/health reporters. Commands are dispatched by the `Communication` class when a matching `cmd/` ZeroMQ message arrives.

### Frontend↔backend

The React frontend communicates with Flask exclusively via **Socket.IO** (not REST). The Flask server emits module state, health, and recording events; the frontend sends commands back as Socket.IO events. The Vite dev server proxies `/socket.io` to `localhost:5000`.

## Conventions

- **Conventional commits** with `feat/`, `fix/`, `refactor/` branch prefixes
- Branch flow: PRs → `staging` → `main`
- Python line length: 88 (ruff). ⚠ pyproject claims py38 compatibility but the code requires **3.11+** (`match` statements, `StrEnum`, numpy ≥ 2.2); all deployed Pis run Bookworm/3.11+.
- Systemd-aware logging: timestamps are skipped when `INVOCATION_ID` env var is set (systemd sets this)
- PTP log parsing lives in `src/*/ptp.py`; health metrics in `src/*/health.py`
- `src/__version__.py` is written by a **pre-commit hook** (`git describe`) so ZIP deploys carry the version. It is inherently one commit behind — never "fix" this by committing a manual bump. The hook itself is tracked at `scripts/git-hooks/pre-commit`, but `.git/hooks/` is never populated automatically from a tracked directory — each clone must run `git config core.hooksPath scripts/git-hooks` once (see `docs/readthedocs/about/contributing.md`). **Found 2026-08-14**: this file had been stale for ~3 weeks / 196 commits — the original hook only ever existed locally, untracked, on one dev's machine, and was silently lost the moment commits started coming from elsewhere. Fixed by tracking the hook script and wiring up `core.hooksPath`; if this goes stale again, check `core.hooksPath` is actually set on whatever machine is committing.
- The frontend variant (basic / loom / apa / habitat / acoustic_startle) is selected at build time via the `VITE_VARIANT` env var, which `saviour-config`'s `build_frontend()` writes; `vite.config.js` resolves the `virtual:active-app` alias to `src/${variant}/App.jsx`, and `main.jsx` imports that alias indirectly through `ThemedApp`. Switching rigs means re-running the build with a different `VITE_VARIANT`, not editing source.

**Not scale-dependent, do sooner than phase 4**: the 2026-07-27 security review (see the Security section in TODO) found items that are risks today regardless of lab size — two hardcoded fleet-wide Samba passwords already committed to the repo, and an unauthenticated-ZMQ path to full RCE-as-root via `update_saviour` that doesn't require ever touching the web UI's login. The web UI *does* already have a real (if limited) auth system, contrary to this roadmap's original "auth on... web UI" framing — what it actually needs is TLS, rate-limiting, and closing the unauthenticated endpoints, not auth from scratch.

**Revised 2026-08-25**: the "real regardless of lab size" framing for the `update_saviour`/ZMQ-RCE item specifically has been reconsidered — see the v1.0 Milestone section's threat-model note below. This system already assumes LAN access is the trust boundary (the same way SSH/physical access to any of these Pis already is); an attack that needs nothing more than that precondition isn't a new risk the codebase is failing to close, it's the accepted model. The hardcoded-Samba-password half of this paragraph is unaffected by that reasoning (a credential committed to git history is compromised regardless of network exposure) and was already fixed independently.

## v1.0 Milestone (proposed 2026-08-13, currently v0.6)

Scope for calling this v1.0: **safe to run unattended on a closed lab LAN without silent data loss or easy compromise** — not "fully hardened for internet exposure." Deliberately excludes the big structural refactors (they're real debt, but don't block correctness/safety): `web.py` blueprint split, the `examples/`→`variants/` manifest rename, Samba→rsync, and the module god-object composition refactor all stay post-1.0.

- [x] **Security floor** — re-scoped 2026-08-25 (see the threat-model note below) to the guest/accident-prevention items; the two unauthenticated-*-but-requires-LAN-access items originally listed here moved to "explicitly deferred":
  - [x] Session recording downloads (`/api/sessions/<name>/download...`) had no auth check at all — **fixed 2026-08-25** (`security/gate-unauthenticated-endpoints`). `_require_auth` itself doesn't reach these routes (they're plain `<a>`-tag GETs with no Socket.IO session, and a browser download click can't attach a custom `Authorization` header), so this needed a short-lived download-token scheme instead: an authenticated socket calls `request_download_token`, gets a token good for 5 minutes, and the frontend's `triggerDownload()` appends it to every download URL transparently.
  - [x] Gated the other unauthenticated data-leak endpoints — **fixed 2026-08-25**: `/facade/list_modules`, `/facade/module_health`, `/facade/exported_recordings` now check the same `Authorization: Bearer <password>` header `/facade/send_command` already used (via a new shared `_check_bearer_auth` helper — confirmed these three are external-script-only routes, never called by the browser frontend, so no frontend changes were needed); `get_bug_report` now requires login, and its `bug_report_status`/`bug_report_ready` emits are scoped to `room=requester_sid` instead of broadcasting the diagnostics-zip download link to every connected guest. `/update/package` deliberately left as-is — see the threat-model note below.
  - [x] Guest-only UI controls that call these now-gated handlers were still clickable, just silently rejected — found live (**"Sync to All Modules" clickable as guest**, Settings → Controller → Export) and **fixed 2026-08-25** for both that button and its per-module "Sync credentials from controller" sibling, disabled via the existing `useIsLoggedIn()` pattern already used by `ModuleActionsMenu`/`ControllerActionsMenu`/`TTLConfigCard`/`System.jsx`.
- [ ] **Explicitly deferred, documented as known limitation for v1.0** — **threat-model note, 2026-08-25**: this system already assumes **LAN access is the trust boundary** — anyone who can reach the network is treated as authorized, the same way SSH/physical console access to any of these Pis already is. The web UI's guest/admin split exists to stop an operator *accidentally* breaking a running experiment or leaking data (wrong button, mid-session config change), not to defend against a malicious LAN-resident actor — fixing something whose only attacker precondition is "already has LAN access" doesn't change the system's actual exposure. On that basis, two items originally in the Security floor list above move here instead:
  - **`update_saviour` / `deploy_update` package signature or checksum verification** (currently only checks `zipfile.is_zipfile()`) and **ZMQ `ROUTER_HANDOVER` identity-hijack** (a spoofed `module_id` can silently steal another module's command stream) — both originally flagged in the 2026-07-27 review as "real regardless of LAN-vs-WAN exposure," but both require nothing more than LAN access to exploit, exactly the precondition already accepted as trusted everywhere else in this system. Revisit only if the threat model itself changes (e.g. an untrusted-BYOD or multi-tenant LAN, or the controller doubling as an internet gateway per the existing WAN-exposure caveats below).
  - `/update/package` staying unauthenticated is a direct corollary of the `update_saviour` decision above: it's fetched by modules via plain `requests.get()` with no admin password available to them, so gating just this one route would break real fleet updates without changing the system's actual exposure (the ZMQ command that triggers the fetch is equally unauthenticated either way).
  - Also here, unchanged from the original list: ZMQ CURVE auth/encryption, web UI TLS, Samba SMB3 sealing, fleet SSH-key/password rotation on clone — the roadmap already frames these as "closed-LAN only" caveats; v1.0 ships with that caveat stated plainly rather than blocked on the multi-day transport-layer work.
- [ ] **Process**: wire the existing `python-app.yml` CI job up as a *required* status check on `main`/`staging` before tagging v1.0 (see GitHub repo settings section below) — a tagged release should not be possible to cut from a red build.

### Security (found 2026-07-27 review)

Threat model: a local network of Raspberry Pi 5s (one controller, several modules), typically a closed lab LAN — but the controller (or a separate router) sometimes acts as the internet gateway, and devices are provisioned either by a user running `install.sh` themselves or by flashing pre-baked cloned SD card images (`scripts/multiclone.sh`) across a fleet. Several items below are only "acceptable" as long as the LAN stays closed and stop being acceptable the moment it's bridged.

**Revised 2026-08-25**: the line above used to end "...but the credential and RCE items are real regardless of network exposure." That framing has been reconsidered — see the v1.0 Milestone section's threat-model note. This system already treats LAN access itself as the trust boundary; the web UI's guest/admin split is about preventing an operator from *accidentally* breaking a running experiment, not about defending against a malicious LAN-resident actor. So `update_saviour` signature verification and the ZMQ identity-hijack item below are deliberately deferred (not fixed) — both require nothing more than LAN access to exploit, which this system already accepts as trusted everywhere else. The web-UI-facing items (session downloads, the `/facade/*` GETs, `get_bug_report`) are a different category — those are about a *guest browser session* (no special network position needed, just an open tab) being able to do more than intended — and have been fixed; see their entries below.

- [ ] **`update_saviour` is a full unauthenticated RCE-as-root primitive** — it's a `@command()`-registered ZMQ RPC (`module.py`) that takes a **caller-supplied** `controller_url`, downloads `{controller_url}/update/package` over plain HTTP with no signature/checksum check (only `zipfile.is_zipfile()`), `rsync`s it over the install directory, and restarts the service as root. Since the ZMQ command bus has no auth (below), any device that can reach a module's DEALER connection can point this at an attacker-controlled server and get arbitrary code execution as root — without ever touching the web UI's login. The web-UI-driven deploy path (`deploy_update`/`stage_current_version` in `web.py`) is properly gated behind the admin password but has the same total absence of package integrity/authenticity verification. **Deliberately deferred for v1.0, 2026-08-25** — see the threat-model note above and the v1.0 Milestone section: this requires nothing beyond LAN access, which the system already treats as trusted.
- [ ] **ZMQ command bus: no auth, no encryption, and an identity-hijack path** — ROUTER (5555) and PUB/SUB (5556) bind `tcp://*` with no CURVE security. `ROUTER_HANDOVER=1` means any device that opens a DEALER socket, sets its identity to a real module's `module_id`, and sends `"hello"` immediately displaces that module's routing entry — the controller's commands (including Samba credentials via `set_export_config`, `shutdown`, `update_saviour`) then go to the attacker instead of the real module. Remotely-callable commands with no auth at all include `shutdown`, `reboot`, `update_saviour`, `reset_config`, `set_export_config` (redirects a module's export to an attacker-controlled share), and rig-specific physical actuators (e.g. APA's shock/motor control). **Deliberately deferred for v1.0, 2026-08-25** — same reasoning as `update_saviour` above.
- [ ] **Web UI: single shared password, sent and stored in plaintext, no lockout** — Flask-SocketIO is served over plain HTTP (`host='0.0.0.0'`, no TLS anywhere), so the admin password is sniffable on every login and reconnect. The frontend (`authStorage.js`) caches it in `localStorage` indefinitely and resends it on every reconnect. `handle_login` has no rate-limiting/lockout and never logs failed attempts, so once an operator sets a memorable password (min length is only 8 chars) nothing slows down guessing it. `cors_allowed_origins="*"` widens this further.
- [x] **Several endpoints leak fleet data with no auth at all** — `/facade/list_modules`, `/facade/module_health`, `/facade/exported_recordings`, and `/update/package` (the staged update zip itself) have no auth check, unlike `/facade/send_command`. `get_bug_report` is also unauthenticated, and its `bug_report_ready` event (carrying the diagnostics-zip download token) is broadcast to **every connected socket** instead of just the requester (missing `room=request.sid`, inconsistent with every other emit in the file) — any guest gets a live link to a bundle of raw, unredacted `journalctl` output. ### Architectural concerns

These are larger structural issues that require significant refactoring. Recorded here so they are not lost.

- [ ] **Module base class is a god object** — `module.py` (~1275 lines) owns config, export, PTP, recording, health, network, commands, and lifecycle. No concern can be tested in isolation; contributors must understand the entire base before writing a single sensor. High effort — requires composition refactor across all module types.
- [ ] **`web.py` is a 2000-line grab-bag** (found 2026-07-09 review) — sessions, config sync, chunked update uploads, deployments, bug-report collection, NAS probing (three duplicated mount/umount snippets with different mount points), time setting, and power control all live in two giant registration methods. Split into Flask blueprints / per-concern services. The indentation bug above is a direct symptom.
- [ ] **Unsupervised threading + broad exception policy** (found 2026-07-09 review) — 59 ad-hoc `threading.Thread(daemon=True)` spawns and ~280 `except Exception` handlers. A crashed monitor/retry thread dies silently and its job simply stops happening. Consider a tiny supervised-thread helper (log-and-restart) for the long-lived loops, and narrower exceptions on the data path.
- [ ] **`modules/communication.py`: heartbeat-watchdog force-reconnect crashed the whole process with a fatal libzmq assertion, mid-recording** (found live 2026-08-20, testing `habitat_camera` on `habitat-camera-module-d074`) — `journalctl` showed: `2 consecutive heartbeat acks missed — command channel appears dead, forcing ZMQ reconnect` → `_force_reconnect()` → `cleanup()` closes the command socket → a few seconds later, `Assertion failed: pfd.revents & POLLIN (src/signaler.cpp:238)` → `systemd`: `Main process exited, code=killed, status=6/ABRT`. This is a fatal libzmq-level assertion, not a Python exception — it can't be caught, it kills the process outright via `abort()`. Not a regression from anything touched today; pre-existing in the shared `Communication` class used by every module type. Likely cause: `_force_reconnect()`'s `cleanup()` (spawned in its own thread by the ack watchdog) closes/tears down `command_socket`/`context` while `listen_for_commands()`'s listener thread may still be blocked inside a receive call on the same socket — a known-fragile pattern in libzmq, even though the code already tries to sequence this carefully (closing the socket first specifically to unblock the listener, per its own comment at `communication.py:453-456`). Also found, un-confirmed as the actual trigger here but a real gap regardless: `_schedule_reconnection()`/`_attempt_reconnection()` (the *other*, independent reconnect path, triggered by "Connection refused"/"No route to host" errors in the listener's exception handler) does **not** acquire `_reconnect_lock` — nothing stops it from tearing down/rebuilding the same `command_socket`/`context` concurrently with a heartbeat-watchdog-triggered `_force_reconnect()`. Not chased further today — `systemd` already auto-recovers the process within ~10s (`Restart=` already configured, `Scheduled restart job, restart counter is at 1` in the log), so this is a rough restart rather than silent data loss, and root-causing a libzmq C-level threading assertion properly would need more time than today's session had. Next step if picked up: make `_schedule_reconnection`/`_attempt_reconnection` share `_reconnect_lock` with `_force_reconnect` regardless of whether it's the actual cause here (it's a real unguarded concurrency gap either way), then look at whether `listen_for_commands()` needs a way to signal "I've returned from recv and am not about to re-enter it" before `cleanup()` proceeds past the socket close, rather than relying on close-from-another-thread alone to unblock it safely.
- [ ] **Controller/module/frontend "variant" selection is hardcoded and conflates three separate axes of change** (found 2026-08-01 discussion, prompted by writing `about/contributing.md`) — `saviour-config` hardcodes two whiptail menus, `select_controller_type()` (5 entries: basic/apa/habitat/acoustic_startle/loom) and `select_module_type()` (8 entries), that must be kept in sync by hand with the `src/controller/variants/*/`, `src/modules/variants/*/`, and `src/controller/frontend/src/*/` folders. Worse, a single `DEVICE_TYPE` string drives three things simultaneously: `get_python_path()`'s `src/controller/variants/${DEVICE_TYPE}/${DEVICE_TYPE}_controller.py` convention (and the module equivalent), and `build_frontend()`'s `VITE_VARIANT=${DEVICE_TYPE}`. This forces a 1:1 pairing between "new frontend variant" and "new controller Python class" even when the variant needs zero backend logic. Concrete evidence this is already costing real weight: `loom_controller.py` is a pure no-op subclass (empty `handle_special_module_status`, empty `configure_controller`) that exists solely to satisfy the one-class-per-type convention, whereas `apa_controller.py` is a genuine case that needs its own class — real `handle_special_module_status` cases for `arduino_state`/`shock_started_being_delivered`/`shock_stopped_being_delivered`/`zone_entered`/`zone_exited`, plus its own `apa_web.py` route file. The module side has the analogous problem without the frontend axis: e.g. `rfid`'s variant folder currently has only a config JSON and no module class yet, and there's no way to tell `saviour-config` "this new device type is behaviourally a TTL module with different config" without duplicating a whole `src/modules/variants/<type>/` folder — even where a shared base class (`CameraBase`, per the camera-family unification above) already covers the difference through config alone.

## Hardware gotchas

### AudioMoth USB microphone

- **Device name encodes sample rate.** The AudioMoth firmware names its USB audio device after its current sample rate (e.g. `250kHz AudioMoth USB Microphone`). Calling `configure_audiomoth()` to change the rate causes PulseAudio/PipeWire to drop the old device ID and register a new one. Any code that stores a PulseAudio device ID (e.g. `self.audiomoths`) must re-discover after reconfiguration — otherwise `soundcard.get_microphone(id)` raises `IndexError` intermittently while the monitoring stream (opened at startup) keeps working on the stale stream.
- **Effective bandwidth is much lower than Nyquist at low sample rates.** The EFM32's PDM decimation filter provides only a fraction of the theoretical bandwidth: ~5 kHz usable at 48 kHz, ~20 kHz at 96 kHz, ~70 kHz+ at 192 kHz. 192 kHz is the only rate suitable for ultrasonic rodent vocalisation work. Do not assume Nyquist = usable bandwidth when validating or warning about sample rate choices.
- **Monitoring and recording use separate soundcard recorders** on the same physical device. PipeWire supports multiple simultaneous readers, so this is intentional and works correctly.

### Controller clock (PTP grandmaster)

- The controller runs `phc2sys` to discipline the system clock from its PTP hardware clock. This means `systemd-timesyncd` / NTP is active and `timedatectl set-time` will fail with *"Automatic time synchronization is enabled"*. Any code that sets the system time must disable NTP first (`timedatectl set-ntp false`), set the time, then re-enable it (`timedatectl set-ntp true`) — ideally in a try/finally.

### Hailo AI HAT / PCIe driver (`apa_camera`, `lightning_camera`)

- **`hailort-pcie-driver` needs `dkms` installed *before* it does, or it silently falls back to an unmanaged one-off kernel module build that breaks again on the next kernel upgrade** (found 2026-08-18, diagnosing a Pi where `hailortcli scan`/`fw-control identify` reported no devices found despite `lspci` showing the Hailo chip fine). The driver package's postinst tries to register the module with DKMS; if `dkms` isn't present yet it prints `Failed to install PCIe driver to the DKMS tree. Trying to install PCIe driver without DKMS` and builds a plain module for the *currently running* kernel only — nothing rebuilds it on the next `apt upgrade` that bumps the kernel, so it silently goes missing again (`modprobe hailo_pci` then fails with `Module hailo_pci not found in directory /lib/modules/<new-kernel>`). `configure_module_dependencies()` (`saviour-config`) just did `apt-get install -y hailo-all` with no `dkms` dependency ensured first — fixed by adding `dkms` ahead of `hailo-all` in both `apa_camera`'s and `lightning_camera`'s `variant.conf` `APT_PACKAGES` (order matters: the loop installs packages one at a time in list order, so `dkms` must come first to be present when `hailo-all`'s `hailort-pcie-driver` postinst runs). This only fixes *new* installs — an already-provisioned Pi in this state needs a one-time manual fix: `sudo apt install dkms && sudo apt install --reinstall hailort-pcie-driver && sudo reboot`.
- **Diagnostic order for "Hailo device not found"**: `lspci | grep -i hailo` first (is the PCIe link even up? if not, check `dtparam=pciex1`/`dtparam=pciex1_gen=3` in `/boot/firmware/config.txt`, needs a reboot after adding) → `lsmod | grep hailo` (is the kernel module loaded at all?) → `dmesg | grep -i hailo` (load attempted and failed, or never attempted?) → `dkms status` (built against the running kernel, per `uname -r`, or a stale one?).
- **Hailo-8 vs Hailo-8L**: `lspci | grep -i hailo` also names the actual chip (`Hailo-8 AI Processor` vs a Hailo-8L one) — worth checking before deploying a `.hef`, since `tools/convert_to_hailo.py`'s `--hw-arch` defaults to `hailo8l` (the standard AI Kit chip) but some devices carry the full Hailo-8 (26 TOPS vs 13 TOPS) instead.

### Pi 5 PoE power delivery (NVMe controllers + PoE HAT modules)

Every device in the fleet is a Pi 5 powered over PoE rather than USB-C — controllers via the 52Pi EP-0240 M.2 NVMe M-Key PoE+ HAT, most modules via the Waveshare "PoE HAT (F)". Both surfaced real findings from the same live incident.

- **NVMe autonomous power-state transitions (APST) can wedge the whole device, requiring a manual power cycle to recover** (found 2026-08-25, live on a habitat controller booting from a Kingston SKC3000S512G over PCIe) — diagnosed from `journalctl -b -1 -k`: three separate bursts of `nvme nvme0: I/O tag ... timeout, aborting req_op:WRITE` across one ~22h uptime (Aug 24 15:22, Aug 25 09:17, Aug 25 09:45), each aborting 4 in-flight writes on the same queue. The first two recovered (`Abort status: 0x0` followed by normal operation); the third did not — the journal goes completely silent ~2 minutes later and stays silent for ~5 hours until a manual power cycle, the signature of the root filesystem (and therefore everything, including logging) hanging. Ruled out undervoltage first (`vcgencmd get_throttled` was `0x0` for the whole boot, so not a power-supply problem by itself). The standing cause on this Pi 5 + NVMe combination is APST: the kernel's default `nvme_core.default_ps_max_latency_us` (100000, i.e. 100 ms) lets the drive drop into a deep power-saving state between writes, and it can fail to wake up in time — usually just the recoverable timeout/abort, but on a bad occurrence the controller never comes back.
  - **Fix**: append `nvme_core.default_ps_max_latency_us=0` to `/boot/firmware/cmdline.txt` (disables APST) and reboot. Applied automatically — `setup.sh`'s `configure_nvme_power_management()` (fresh installs) and `mend.sh` step 7/9 (already-deployed devices) both check `/sys/class/nvme/nvme0` and append the parameter idempotently if missing, each printing a reminder that a reboot is required. NVMe-specific, so only controllers hit this path — modules have no NVMe root.
  - Fleet devices cloned via `multiclone.sh` inherit it automatically since that script only patches the PARTUUID in `cmdline.txt`, not the rest of the line — as long as the *master* image the clone is taken from has had `setup.sh`/`mend.sh` run on it since this fix landed.
- **`PSU_MAX_CURRENT` (bootloader EEPROM config) was found completely unset on the same controller** — the Pi 5 bootloader normally learns a high-amp supply is present via USB-C PD negotiation, which never happens over a GPIO-header PoE HAT, so it silently defaults to a conservative 3A current budget instead of the ~4.5A both the EP-0240 (controllers) and the Waveshare PoE HAT (F) (modules) can actually deliver. Both vendors' own wikis document `PSU_MAX_CURRENT=5000` as a required setup step, independent of any NVMe symptom — plausibly a contributing factor to the hang above (a power budget shortfall under peak simultaneous load), but worth fixing fleet-wide regardless of whether a given device has ever shown a symptom.
  - **Fix**: `sudo rpi-eeprom-config --apply <config-with-PSU_MAX_CURRENT=5000>`, reboot. Applied automatically, **fleet-wide (not NVMe-gated)** — `setup.sh`'s `configure_psu_max_current()` and `mend.sh` step 8/9 both check for `rpi-eeprom-config` being present (i.e. a real Pi 4/5) rather than for NVMe, since this applies to every device regardless of role. Idempotent: reads the current EEPROM config first and only reapplies if `PSU_MAX_CURRENT` is missing or wrong.
  - **Caveat found while applying this live**: `rpi-eeprom-config --apply <file>` defaults to bundling the *latest available* bootloader firmware release when the file argument doesn't pin a specific `.bin` image — so applying just this one config line can also silently bump the bootloader firmware version itself (same "default"/stable channel, not beta). Harmless in practice (routine same-channel update, SD-card rescue image available if it ever goes wrong) but worth knowing before assuming this step is a config-only change.
  - Like the NVMe fix, `rpi-eeprom-config` reads the *currently running* config, not what's freshly flashed — so it will not self-report `[OK]` until after the reboot that activates the new EEPROM image.
- **Module-side reboots have now been seen too, not just the controller** (found 2026-08-27, habitat session `CRLLT3-247Cameras-camera-173650` — full write-up in the Habitat deployment live-findings note under Architectural concerns) — 5 of 16 camera modules each did one unexplained full OS reboot over a 19 h session (`health.json` `uptime` reset, segment counter restarted). The diagnostics dump's 2 h journal retention was too short to catch the cause and showed no throttle/voltage lines in-window, so it's unconfirmed — but a `Waveshare PoE HAT (F)` module browning out under sustained encode + hourly concurrent-export load is exactly the `PSU_MAX_CURRENT`-unset scenario above, and worth ruling in/out first with the checklist below on the affected Pis (`camera_34ec`, `camera_a2d2`, `camera_d549`, `camera_d586`, `camera_98b7`).
- **Each recording session now exports its own journal snapshot** (added 2026-08-27, `fix/habitat-session-followups`) — `Recording.stop_recording()` writes `<session>_<module>_journal_(<ts>).txt` (saviour.service + kernel, `--since` the recording start) into `to_export/`, so it rides the normal export to the share next to the footage. This is the durable copy for a weeks-long unattended run where the on-device journal has long rotated and nobody was watching when a module rebooted. Best-effort (never raises out of a stop); toggle with `recording.export_session_journal` (default on). Routed to the session folder by the same `_extract_session_from_filename` marker the health-metadata CSVs use.
- **Export Diagnostics bundle now includes previous-boot + kernel journals** (added 2026-08-27, `fix/habitat-session-followups`) — it used to be `journalctl -u saviour.service -n 500` per side (current boot, unit only, no kernel), which is structurally blind to a reboot cause. Now each module returns, and the zip carries per module: `logs.txt` (current boot, 3000 lines), `logs_prevboot.txt` (`-b -1`, why the service last stopped), `kernel_prevboot.txt` (`-k -b -1`, the reboot cause), `boots.txt` (`--list-boots`); the controller side adds `kernel.txt` (current boot) too and bumps `logs.txt` to 5000 lines. Depends on persistent journald (below) actually being on, and `-k` needs the service user able to read the kernel journal — failures are captured as text in the file rather than dropped. Older modules that predate the new fields still bundle fine (controller only writes keys that are present).
- **Persistent journald was OFF on a deployed module despite being in `setup.sh` + `mend.sh` since 2026-06-29** (found 2026-08-27 on `camera-module-34ec`: `journalctl -b -1` → *"no persistent journal was found"*, `journalctl --list-boots` shows only the current boot, `/run/log/journal` is a ~2 h RAM ring — so **no module reboot is post-hoc diagnosable** until this is fixed). Both scripts write `Storage=persistent` to `/etc/systemd/journald.conf` and restart journald, so the modules were almost certainly cloned from a master SD image predating that commit and never re-mended (`multiclone.sh` does not run `setup.sh`/`mend.sh`). Fix fleet-wide: `run_mend` (or `sudo bash mend.sh`) on every module, then confirm `journalctl --list-boots` lists more than one boot. Do this **before** chasing the 5 module reboots above — without it the next occurrence is just as blind. (Note `mend.sh` step 6 `tee`s the whole `journald.conf`, so it also wipes any other journald tuning — not a concern on this fleet, which doesn't set any.)
- **`mend.sh` reboot marker: `/run/reboot-required`** — `mend.sh` writes this file (a one-line `saviour mend: NVMe APST / PSU_MAX_CURRENT change pending reboot` reason) whenever step 7 (NVMe APST) or step 8 (`PSU_MAX_CURRENT`) *actually changed* something, and exits `10` instead of `0`. It's deliberately the **same path Debian's `update-notifier` uses**, so existing "reboot pending" tooling picks it up, and it's on tmpfs so it self-clears on the reboot that resolves it. `mend.sh --reboot` (opt-in, default off) reboots at the end iff this marker was written; `run_mend(reboot=True)` passes that through, and `run_mend`'s reply is `{"result": "reboot_required"}` (still a success) when it sees exit 10. To find fleet devices that were mended but never rebooted: `[ -f /run/reboot-required ] && echo pending` across the fleet, or check for exit-10 in `/var/log/saviour-mend.log`. See the (now `[x]`) mend.sh TODO item above for the full implementation.
- **Diagnostic checklist for "Pi went unreachable, needed a power cycle"** on any Pi 5 in this fleet: `journalctl --list-boots` to find the gap and which boot preceded it → `journalctl -b -1 -k -g nvme` for timeout bursts (NVMe devices only) → `vcgencmd get_throttled` to check for a flagged undervoltage event (note this is a live/sticky-since-boot read, not historical — a `0x0` today doesn't rule out an event on the *previous* boot with certainty, but the absence of any voltage-warning kernel log lines in that boot's journal does) → `sudo rpi-eeprom-config | grep PSU_MAX_CURRENT` (missing/wrong means the firmware may have been power-budget-limiting under load; `[ -f /run/reboot-required ]` means a `mend.sh` run already queued the fix but the device hasn't rebooted to activate it) → for NVMe devices additionally `cat /sys/class/nvme/nvme0/power/control` (`auto` means APST is active) and `/sys/module/nvme_core/parameters/default_ps_max_latency_us` (100000 = default/unmitigated).

### Module offline detection

- Modules do **not** send a graceful mDNS goodbye on ungraceful disconnection (power loss, switch unplug). The heartbeat timeout (90 s, `HEARTBEAT_TIMEOUT_SECS` in `modules.py`) is the only mechanism for detecting these. The `last_heartbeat_time` field on `Module` must be non-zero before the timeout logic fires, so newly registered modules with no heartbeat yet are not immediately evicted.

### PTP network topology (multi-switch habitats)

The controller is the PTP grandmaster; every module is a slave disciplining its
PHC from it. The fleet switches (habitat rigs use **TP-Link TL-SG1218MPE**,
16-port Gigabit PoE+ "Easy Smart") are **plain L2 — not IEEE 1588 transparent
or boundary clocks**. That has two consequences `ptp4l` cannot correct for:

- **Every switch hop adds variable queuing (residence) delay** to PTP event
  messages. A non-PTP switch does not measure or subtract it, so it shows up as
  offset jitter that grows with hop count.
- **Bulk traffic on a shared link delays PTP packets** — a Samba export frame
  in flight makes the next Sync/Delay_Req wait behind it. The controller's
  `ExportQueue` caps this at `max_concurrent_exports` (2), but 2 concurrent
  ~250 MB transfers across the same trunk a module syncs over is still enough
  to nudge a marginal slave over threshold.

**This is fixed by wiring, not code.** SAVIOUR must stay topology-agnostic; do
not add QoS-tuning, VLAN-aware logic, or per-habitat network assumptions to the
codebase. The standard for any habitat, independent of module count:

1. **Grandmaster (controller) and the export share on the same switch.** That
   switch is the PTP root.
2. **No module more than 2 switch hops from the controller** (1 is ideal).
3. **No third switch in the PTP path.** With two habitat switches, link them
   *directly* to each other — use the MPE's SFP ports, SFP-to-SFP — not via an
   aggregation switch.
4. If a building uplink is needed (internet for NTP fallback / Teams / ZIP
   deploys), hang it off **one** habitat switch as an edge port so grandmaster
   traffic never traverses it.
5. Beyond 2 switches per habitat, or if contention persists at 2 hops, the
   answer is **PTP transparent-clock switches**, not config — a TC subtracts
   its own residence time, so hop count and export load stop mattering.

**Found 2026-08-27** (habitat session `CRLLT3-247Cameras-camera-173650`, see the
Architectural-concerns live-findings note): two TL-SG1218MPEs joined *via a
third switch* gave far-side modules a 3-hop uncorrected path vs 1 hop for
modules on the controller's switch, matching the clean-vs-marginal split
(8 stable / 12 unstable, the 12 including all 4 microphones). Remedy for that
rig: direct SFP link between the two switches, controller + share on one of
them, middle switch demoted to edge-uplink-only — targeting 2 hops max. Confirm
before/after by mapping module MAC → switch port (each switch's web GUI,
Monitoring → MAC address table) against the controller's `ip neigh`, and by a
fresh `/api/ptp_history.csv` a day after the rewire. Note this was a *secondary*
contributor — the primary cause of the hourly sync episodes was the
`_check_ptp_health()` restart loop (fixed on `fix/ptp-auto-restart-feedback-loop`);
re-measure after that lands before deciding how much the rewire still buys.

### Camera framesync (multi-camera timing)

The camera module supports `camera.sync_mode: "server" | "client" | "none"`. This uses **libcamera's software sync mechanism**, not GPIO. The server broadcasts timing packets over UDP; clients adjust their framerate to match. Key facts:

- **`SyncTimer` metadata**: counts down (in µs) to the agreed sync point, then goes negative. A very negative value (e.g. −26 seconds) means sync was established long before recording started — not an error.
- **`SyncReady` metadata**: True on the single frame where synchronisation fires. The encoder's `sync_enable = True` flag discards frames until this fires, then starts recording. `SyncFrames` is set in `_pre_create_first_segment()` to force a fresh sync point close to T=0. The per-frame timestamp CSV is opened in `_start_new_recording()` (not `_pre_create_first_segment()`) so CSV row 0 always corresponds to video frame 0.
- **Phase offset**: Even after sync-lock, there is a fixed per-session inter-camera phase offset (typically 0–8333 µs at 120 fps). This is a hardware characteristic of when the client's frame clock happened to be when sync was established — **not** a PTP error. It is constant within a session and can be calibrated out from the `framesync_per_frame.csv` sidecar.
- **120 fps limitation**: libcamera sync requires the target framerate to be significantly below the camera's maximum so the client can speed up to catch the server. At 120 fps on Pi Camera Module 3 (which maxes at ~120 fps at the recording resolution), the client has no headroom and cannot phase-lock. The `sync_enable` / `SyncFrames` approach is still used (best-effort), with a 2-second fallback timeout.
- **PTP two-servo rule**: `ptp4l` disciplines the PHC; `phc2sys` disciplines `CLOCK_REALTIME`. The recording-**start** gate (`_check_ptp_sync` in `recording.py`, called from every start path) checks both `ptp4l_offset` and `phc2sys_offset` against **`recording.ptp_start_gate_us`** (default **50 µs**, its own key since 2026-08-28 — split off `ptp_threshold_us`, which is now only the looser mid-recording "degraded" *warning*, ~1 ms). Both keys are on the Settings → Thresholds tab. `phc2sys_freq` (the frequency correction in ppb) reflects the crystal oscillator's natural offset and is typically 20,000–30,000 ppb on settled hardware — **this is normal and should not be gated on**. What matters is the *difference* between cameras' freq values, not the absolute magnitude. Wait at least 5–10 minutes after a camera reboot before recording for phc2sys to converge its frequency estimate to the correct value for that crystal.
- **Framesync analysis**: `tools/analyse_framesync.py` reads per-session timestamp CSVs and reports inter-camera offset statistics including clock drift (µs/sec) and detrended jitter (the true timing noise floor once slow PTP drift is removed). Run with `source env2/bin/activate` (needs pandas). The "mean offset" includes the fixed phase offset; the **detrended p95** is the meaningful accuracy figure (<20 µs with settling PTP, <5 µs when fully converged).
