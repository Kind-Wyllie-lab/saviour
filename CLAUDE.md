# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

SAVIOUR (Synchronised Audio Video Input Output Recorder) is a modular, PoE-networked multi-sensor recording system for rodent behavioural research. Each Raspberry Pi 5 on the network runs either as the **controller** or as a **module** (camera, microphone, TTL, RFID, etc.).

## Architecture

### Two-role system

Every device runs one of two roles, set in `/etc/saviour/config`:

- **Controller** (`src/controller/`) — PTP grandmaster, mDNS service discovery, ZeroMQ command hub, Flask+SocketIO web interface on port 5000, recording session orchestration, file export queue to Samba/NAS.
- **Module** (`src/modules/`) — PTP slave, registers via Zeroconf, connects to controller's ZeroMQ sockets, records to `/var/lib/saviour/recordings`, exports files to the controller's Samba share.

The concrete implementations live under `src/controller/variants/` and `src/modules/variants/` (renamed from `examples/` 2026-08-13 — see the Architectural concerns section below for what did and didn't come with that rename). Each variant subclasses the abstract `Controller` or `Module` base class.

### Inter-service communication

ZeroMQ **ROUTER/DEALER** is used for controller→module commands; modules publish status/heartbeats on a PUB/SUB socket:

- Controller binds a ROUTER socket (port 5555); each module connects a DEALER socket with its `module_id` as the ZMQ identity and sends a `"hello"` frame on connect to register.
- Controller tracks connected dealers in `_connected_dealers`; heartbeat timeout evicts a module and calls `remove_dealer()`.
- Modules publish status/heartbeats on `status/<module_id>` (PUB, port 5556); controller SUBs to all topics.
- **Actual wire format**: commands are plain strings `"{command} {json_params}"` routed to the DEALER by identity; status messages are JSON dicts with `type`, `timestamp`, `module_id`, `module_name` plus type-specific fields. There is no envelope, no `msg_id`, and no ack correlation.
- ⚠ `docs/PROTOCOL_V1.md` is **aspirational, not descriptive** — it documents PUB/SUB `cmd/` topics and a JSON envelope with `msg_id`/ack/retry semantics that were never implemented. Do not use it as a reference for the current protocol.

### Config layering

JSON config is merged in three layers: `base_config.json` → `active_config.json` → `.env` overrides. Keys prefixed with `_` are internal defaults not meant to be overridden by users. The `Config` class in `config.py` handles this for both controller and module sides.

### Module command system

Module methods decorated with `@command()` are auto-registered as remotely callable RPCs. `@check()` registers status/health reporters. Commands are dispatched by the `Communication` class when a matching `cmd/` ZeroMQ message arrives.

### Frontend↔backend

The React frontend communicates with Flask exclusively via **Socket.IO** (not REST). The Flask server emits module state, health, and recording events; the frontend sends commands back as Socket.IO events. The Vite dev server proxies `/socket.io` to `localhost:5000`.

## Conventions

- **Conventional commits** with `feat/`, `fix/`, `refactor/` branch prefixes
- Branch flow: PRs → `staging` → `main`
- Python line length: 88 (ruff). ⚠ pyproject claims py38 compatibility but the code requires **3.11+** (`match` statements, `StrEnum`, numpy ≥ 2.2); all deployed Pis run Bookworm/3.11+.
- Systemd-aware logging: timestamps are skipped when `INVOCATION_ID` env var is set (systemd sets this)
- PTP log parsing lives in `src/*/ptp.py`; health metrics in `src/*/health.py`
- `src/__version__.py` is written by a **pre-commit hook** (`git describe`) so ZIP deploys carry the version. It is inherently one commit behind — never "fix" this by committing a manual bump. The hook itself is tracked at `scripts/git-hooks/pre-commit`, but `.git/hooks/` is never populated automatically from a tracked directory — each clone must run `git config core.hooksPath scripts/git-hooks` once (see `docs/readthedocs/about/contributing.md`). **Found 2026-08-14**: this file had been stale for ~3 weeks / 196 commits — the original hook only ever existed locally, untracked, on one dev's machine, and was silently lost the moment commits started coming from elsewhere. Fixed by tracking the hook script and wiring up `core.hooksPath`; if this goes stale again, check `core.hooksPath` is actually set on whatever machine is committing.
- The frontend variant (basic / loom / apa / habitat / acoustic_startle) is selected at build time via the `VITE_VARIANT` env var, which `saviour-config`'s `build_frontend()` writes; `vite.config.js` resolves the `virtual:active-app` alias to `src/${variant}/App.jsx`, and `main.jsx` imports that alias indirectly through `ThemedApp`. Switching rigs means re-running the build with a different `VITE_VARIANT`, not editing source.

## Roadmap (2026-07-09 review; security items added 2026-07-27)

Phased plan derived from a full codebase review. Detailed items live in the TODO lists below.

1. **Stabilise (days)** — fix the web.py handler-registration indentation bug, the overnight-schedule bug, and the offline-install build-isolation failure; make CI actually run (PR triggers, module tests in testpaths, ruff installed and converged).
2. **Consolidate (weeks)** — extract a shared `CameraBase` from the three camera forks; split web.py into blueprints; dead-code sweep (database.py, broken NAS listing, fake login); rewrite PROTOCOL_V1.md to match reality.
3. **Harden (when touching transport)** — add `msg_id` correlation to commands (the one remaining transport gap now DEALER/ROUTER is in); supervised long-lived threads; the multi-module integration test.
4. **Strategic (only if the system outgrows one lab)** — replace Samba export with rsync/HTTP; module base-class composition refactor.

**Not scale-dependent, do sooner than phase 4**: the 2026-07-27 security review (see the Security section in TODO) found items that are risks today regardless of lab size — two hardcoded fleet-wide Samba passwords already committed to the repo, and an unauthenticated-ZMQ path to full RCE-as-root via `update_saviour` that doesn't require ever touching the web UI's login. The web UI *does* already have a real (if limited) auth system, contrary to this roadmap's original "auth on... web UI" framing — what it actually needs is TLS, rate-limiting, and closing the unauthenticated endpoints, not auth from scratch.

## v1.0 Milestone (proposed 2026-08-13, currently v0.6)

Scope for calling this v1.0: **safe to run unattended on a closed lab LAN without silent data loss or easy compromise** — not "fully hardened for internet exposure." Deliberately excludes the big structural refactors (they're real debt, but don't block correctness/safety): `web.py` blueprint split, the `examples/`→`variants/` manifest rename, Samba→rsync, and the module god-object composition refactor all stay post-1.0.

Known issues and planned improvements, grouped by priority. Check these off (`- [x]`) as they are completed.

### High priority — silent data loss / correctness

- [ ] **`pyproject.toml`: `hatchling` in build requires breaks offline module installs** (found 2026-07-09 review) — build backend is `setuptools.build_meta`, so hatchling is never used, but pip's build isolation tries to download it (and setuptools/setuptools_scm) from PyPI on every `pip install -e .`. This is the exact `ERROR: No matching distribution found for hatchling` seen in module journals. Fix: remove hatchling from requires AND use `--no-build-isolation` in mend.sh/update paths; also delete the dead `[tool.hatch.*]` sections.
- [ ] **`recording.py`: `delete_session()`/`clear_ended_sessions()` block on `total_exports_failed > 0` forever, even once every file has genuinely reached the share** (found 2026-08-20, live) — `total_exports_failed` is a lifetime counter (`module_export_update()`, never decremented), by design so an operator can see a session ever had export trouble before deleting it. Combined with the two bugs above, a session that never actually lost anything could still show a permanent "N failed export(s)" warning on delete, since the inflated count from the double-dispatch race was never going to un-increment itself. The two fixes above stop new false failures from being recorded; not changed here: whether `total_exports_failed > 0` alone (as opposed to `pending_exports > 0`, which does clear once resolved) should keep blocking a plain delete forever once `pending_exports` is back to 0, or whether "failed" should only gate on a currently-unresolved failure. Left as `force=True` still available today; worth a deliberate design call rather than a silent behaviour change.
- [ ] **`modules/camera_base.py`: recorded video rotation silently dropped for non-square resolutions at 90°/270°** (found 2026-07-31 review) — `_frame_precallback`'s rotation guard (~line 760) only fires when width==height or rotation==180; the live MJPEG preview rotates unconditionally and correctly in `_stream_post_callback`. An operator sees a correctly-rotated live stream and gets an unrotated recording. Exactly the kind of gap the camera-consolidation item below (Architectural concerns) warns is still outstanding — verify rotation specifically before trusting non-square resolutions on a live rig. **Root cause confirmed 2026-08-14** (reported live on the Home camera): this is a genuine hardware/library limit, not an oversight — the ISP can't do a true 90°/270° transpose on this platform (`_configure_camera`'s comment on `transform` already notes it degrades to a plain flip), and the recorded "main" stream is a fixed-shape DMA buffer the hardware `H264Encoder` reads directly, which can't be reshaped in place the way the live preview's independent `request.make_array()` copy can. A real fix means switching that camera's recording path to software encoding — not attempted here (unverifiable without the physical rig; flagged for whoever picks this up next). **Partial fix landed 2026-08-14**: the frame *content* still isn't rotated, but the baked-in timestamp overlay now is — `_apply_timestamp` gained a `compensate_k` param that renders the timestamp pre-rotated onto the edge that becomes "top" once a viewer rotates the file for playback, so at least the timestamp reads correctly even though the footage itself doesn't turn.
- [ ] **`module.py`: `_check_diskspace()` silently returns `None` instead of a result tuple when free space exactly equals the required threshold** (found 2026-08-04, while adding test coverage) — the two guard branches (~line 1008-1011) are `if free_mb > required_mb: return True, ...` and `if free_mb < required_mb: return False, ...`; the equal case falls through both and the function returns `None`. This is live and reachable: `_check_diskspace` is one of `self.checks`, run on every `validate_readiness()` call (wired to the `validate_readiness` ZMQ command and the web UI's readiness check). `_run_checks()` does `result, message = check()` on the return value, so hitting the exact boundary raises `TypeError: cannot unpack non-iterable NoneType object`. `validate_readiness()`'s outer try/except does catch it, so the operator doesn't get a crash — but they get `{"ready": False, "message": "Error running readiness checks: cannot unpack non-iterable NoneType object"}` instead of an actual disk-space verdict, which is confusing right at the moment disk space is the thing worth knowing about. Fix: change the second guard to `else: return False, ...` (or `>=`/`<=` split).
- [ ] **Nothing verifies a module's recording pipeline is actually still producing data — `is_recording` is a write-once flag, not a liveness signal** (found 2026-08-05 review) — `Health.get_health()`'s `recording` field is `self.recording.is_recording` (`src/modules/facade.py:61`), set `True` once at start and cleared only by a *successful* `stop_recording()`. Nothing re-validates it against whether frames/samples are still flowing: `camera_base.py`'s `_frame_precallback` (~line 812) catches every exception with a bare log-and-continue, so a camera can throw on every frame forever while `is_recording` stays `True`; the microphone's per-device thread (`microphone_module.py:306`) does the same — a USB glitch kills the thread silently with no status sent and no flag reset. Since the controller's own mid-recording safety net (`recording.py`'s `_monitor_sessions()`, ~line 1411, via `facade.is_module_recording()`) reads that exact same boolean, a wedged-but-not-crashed pipeline is invisible end-to-end, not just on the module side. No fix yet — would need some per-pipeline liveness signal (e.g. last-frame-written timestamp compared against expected fps) distinct from the start/stop flag.
- [ ] **`recording.py` (module-side): the one proactive fault-handler that exists — critical-low-disk auto-stop — reports itself identically to an operator-initiated stop, and only checks once per segment boundary** (found 2026-08-05 review) — `_monitor_recording_length`'s disk check (~line 357) only runs inside the `if now - segment_start_time > segment_length` branch, so with e.g. 60-minute segments a disk that fills mid-segment isn't caught until the next boundary. When it does fire, `self.stop_recording()` takes the exact same success path as a manual stop (`{"type": "recording_stopped", "status": "success"}`), so even after the routing fix above there's no fault reason for the controller to distinguish "operator stopped this" from "module force-stopped itself to protect the filesystem" — would need a distinct status/reason field threaded through, plus moving the check outside the segment-boundary gate.
- [ ] **`recording.py` (module-side): `_scheduled_start()` (the `start_at`/FrameSync-aligned start path) runs `_begin_recording()` in a bare daemon thread with no exception boundary** (found 2026-08-05 review) — the synchronous immediate-start path is at least caught by `command.py`'s outer try/except (which now reaches the controller per the fix above); a failure inside the `start_at` thread (e.g. `camera_base.py`'s `_start_new_recording()`, which has no try/except of its own, hitting a busy encoder) propagates only to Python's default thread excepthook (stderr) — no `send_status` of any kind fires. Worth wrapping `_scheduled_start`'s body (or at least the final `_begin_recording()` call) in a try/except that reports via the same `recording_start_failed` path.

### Security (found 2026-07-27 review)

Threat model: a local network of Raspberry Pi 5s (one controller, several modules), typically a closed lab LAN — but the controller (or a separate router) sometimes acts as the internet gateway, and devices are provisioned either by a user running `install.sh` themselves or by flashing pre-baked cloned SD card images (`scripts/multiclone.sh`) across a fleet. Several items below are only "acceptable" as long as the LAN stays closed and stop being acceptable the moment it's bridged — but the credential and RCE items are real regardless of network exposure.

- [ ] **`update_saviour` is a full unauthenticated RCE-as-root primitive** — it's a `@command()`-registered ZMQ RPC (`module.py`) that takes a **caller-supplied** `controller_url`, downloads `{controller_url}/update/package` over plain HTTP with no signature/checksum check (only `zipfile.is_zipfile()`), `rsync`s it over the install directory, and restarts the service as root. Since the ZMQ command bus has no auth (below), any device that can reach a module's DEALER connection can point this at an attacker-controlled server and get arbitrary code execution as root — without ever touching the web UI's login. The web-UI-driven deploy path (`deploy_update`/`stage_current_version` in `web.py`) is properly gated behind the admin password but has the same total absence of package integrity/authenticity verification.
- [ ] **ZMQ command bus: no auth, no encryption, and an identity-hijack path** — ROUTER (5555) and PUB/SUB (5556) bind `tcp://*` with no CURVE security. `ROUTER_HANDOVER=1` means any device that opens a DEALER socket, sets its identity to a real module's `module_id`, and sends `"hello"` immediately displaces that module's routing entry — the controller's commands (including Samba credentials via `set_export_config`, `shutdown`, `update_saviour`) then go to the attacker instead of the real module. Remotely-callable commands with no auth at all include `shutdown`, `reboot`, `update_saviour`, `reset_config`, `set_export_config` (redirects a module's export to an attacker-controlled share), and rig-specific physical actuators (e.g. APA's shock/motor control).
- [ ] **Web UI: single shared password, sent and stored in plaintext, no lockout** — Flask-SocketIO is served over plain HTTP (`host='0.0.0.0'`, no TLS anywhere), so the admin password is sniffable on every login and reconnect. The frontend (`authStorage.js`) caches it in `localStorage` indefinitely and resends it on every reconnect. `handle_login` has no rate-limiting/lockout and never logs failed attempts, so once an operator sets a memorable password (min length is only 8 chars) nothing slows down guessing it. `cors_allowed_origins="*"` widens this further.
- [ ] **Several endpoints leak fleet data with no auth at all** — `/facade/list_modules`, `/facade/module_health`, `/facade/exported_recordings`, and `/update/package` (the staged update zip itself) have no auth check, unlike `/facade/send_command`. `get_bug_report` is also unauthenticated, and its `bug_report_ready` event (carrying the diagnostics-zip download token) is broadcast to **every connected socket** instead of just the requester (missing `room=request.sid`, inconsistent with every other emit in the file) — any guest gets a live link to a bundle of raw, unredacted `journalctl` output. If "stage current version" is ever used, its file walk doesn't exclude `active_config.json`, so a live Samba/Teams-webhook credential could ride along in that same unauthenticated `/update/package` response.
- [ ] **`web.py`: session recording downloads have no auth at all** (found 2026-07-31 review) — `/api/sessions/<name>/download/<file>` and `/api/sessions/<name>/download` (~lines 634-680) have path-traversal guards but never call `_require_auth`, unlike every Socket.IO command handler. Anyone who can reach the web port can download raw recorded video/audio for any session by name — a materially worse gap than the item above, since this is the actual research data rather than just fleet metadata.
- [ ] **No transport encryption on the Samba/CIFS export** — mount commands (`export.py`, `web.py`) never set the SMB3 `seal` option, so recorded research data — and the mount credentials themselves, briefly visible via `ps`/`cmdline` while the mount command runs — cross the LAN in plaintext.
- [ ] **All network services bind to `0.0.0.0` with no interface scoping** — ZMQ ROUTER/SUB and the Flask/SocketIO server listen on every interface. If the controller ever doubles as the internet gateway, the unauthenticated command bus and the sniffable-password web UI become reachable from the WAN side too, not just the PoE LAN. No firewall/iptables rule scopes any of this to `eth0` only.
- [ ] **Fleet image cloning never rotates the OS user's password/SSH keys** — `multiclone.sh` correctly regenerates SSH *host* keys and machine-id automatically for every cloned device, and `clone_prep.sh` covers the same for out-of-pipeline duplication (only if an operator remembers to run it manually). Neither `install.sh`, `setup.sh`, nor any clone script touches the OS user's login password or `~/.ssh/authorized_keys` (`clone_prep.sh` documents leaving `authorized_keys` unchanged as *intentional*) — whatever credential the master image's imager set is shared, unrotated, across every device cloned from it.
- [ ] **`push_credentials.sh` disables SSH host-key checking** (`StrictHostKeyChecking=no`) when pushing Samba credentials to a module, and passes the password as a literal SSH command-line argument (briefly visible via `ps`/`/proc/<pid>/cmdline` on the module during the push).
- [ ] **`saviour.service` runs fully as root with no systemd hardening** — no `NoNewPrivileges`, `ProtectSystem`, or capability bounding, so every finding above has an unrestricted-root blast radius rather than a scoped one. (Reasonable as-is for `ptp4l`/`phc2sys`, which need raw clock hardware access — not obviously necessary for the whole ZMQ/web/update surface.)

### Architectural concerns

These are larger structural issues that require significant refactoring. Recorded here so they are not lost.

- [ ] **Module base class is a god object** — `module.py` (~1275 lines) owns config, export, PTP, recording, health, network, commands, and lifecycle. No concern can be tested in isolation; contributors must understand the entire base before writing a single sensor. High effort — requires composition refactor across all module types.
- [ ] **`web.py` is a 2000-line grab-bag** (found 2026-07-09 review) — sessions, config sync, chunked update uploads, deployments, bug-report collection, NAS probing (three duplicated mount/umount snippets with different mount points), time setting, and power control all live in two giant registration methods. Split into Flask blueprints / per-concern services. The indentation bug above is a direct symptom.
- [ ] **Unsupervised threading + broad exception policy** (found 2026-07-09 review) — 59 ad-hoc `threading.Thread(daemon=True)` spawns and ~280 `except Exception` handlers. A crashed monitor/retry thread dies silently and its job simply stops happening. Consider a tiny supervised-thread helper (log-and-restart) for the long-lived loops, and narrower exceptions on the data path.
- [ ] **`modules/communication.py`: heartbeat-watchdog force-reconnect crashed the whole process with a fatal libzmq assertion, mid-recording** (found live 2026-08-20, testing `habitat_camera` on `habitat-camera-module-d074`) — `journalctl` showed: `2 consecutive heartbeat acks missed — command channel appears dead, forcing ZMQ reconnect` → `_force_reconnect()` → `cleanup()` closes the command socket → a few seconds later, `Assertion failed: pfd.revents & POLLIN (src/signaler.cpp:238)` → `systemd`: `Main process exited, code=killed, status=6/ABRT`. This is a fatal libzmq-level assertion, not a Python exception — it can't be caught, it kills the process outright via `abort()`. Not a regression from anything touched today; pre-existing in the shared `Communication` class used by every module type. Likely cause: `_force_reconnect()`'s `cleanup()` (spawned in its own thread by the ack watchdog) closes/tears down `command_socket`/`context` while `listen_for_commands()`'s listener thread may still be blocked inside a receive call on the same socket — a known-fragile pattern in libzmq, even though the code already tries to sequence this carefully (closing the socket first specifically to unblock the listener, per its own comment at `communication.py:453-456`). Also found, un-confirmed as the actual trigger here but a real gap regardless: `_schedule_reconnection()`/`_attempt_reconnection()` (the *other*, independent reconnect path, triggered by "Connection refused"/"No route to host" errors in the listener's exception handler) does **not** acquire `_reconnect_lock` — nothing stops it from tearing down/rebuilding the same `command_socket`/`context` concurrently with a heartbeat-watchdog-triggered `_force_reconnect()`. Not chased further today — `systemd` already auto-recovers the process within ~10s (`Restart=` already configured, `Scheduled restart job, restart counter is at 1` in the log), so this is a rough restart rather than silent data loss, and root-causing a libzmq C-level threading assertion properly would need more time than today's session had. Next step if picked up: make `_schedule_reconnection`/`_attempt_reconnection` share `_reconnect_lock` with `_force_reconnect` regardless of whether it's the actual cause here (it's a real unguarded concurrency gap either way), then look at whether `listen_for_commands()` needs a way to signal "I've returned from recv and am not about to re-enter it" before `cleanup()` proceeds past the socket close, rather than relying on close-from-another-thread alone to unblock it safely.
- [ ] **Controller/module/frontend "variant" selection is hardcoded and conflates three separate axes of change** (found 2026-08-01 discussion, prompted by writing `about/contributing.md`) — `saviour-config` hardcodes two whiptail menus, `select_controller_type()` (5 entries: basic/apa/habitat/acoustic_startle/loom) and `select_module_type()` (8 entries), that must be kept in sync by hand with the `src/controller/variants/*/`, `src/modules/variants/*/`, and `src/controller/frontend/src/*/` folders. Worse, a single `DEVICE_TYPE` string drives three things simultaneously: `get_python_path()`'s `src/controller/variants/${DEVICE_TYPE}/${DEVICE_TYPE}_controller.py` convention (and the module equivalent), and `build_frontend()`'s `VITE_VARIANT=${DEVICE_TYPE}`. This forces a 1:1 pairing between "new frontend variant" and "new controller Python class" even when the variant needs zero backend logic. Concrete evidence this is already costing real weight: `loom_controller.py` is a pure no-op subclass (empty `handle_special_module_status`, empty `configure_controller`) that exists solely to satisfy the one-class-per-type convention, whereas `apa_controller.py` is a genuine case that needs its own class — real `handle_special_module_status` cases for `arduino_state`/`shock_started_being_delivered`/`shock_stopped_being_delivered`/`zone_entered`/`zone_exited`, plus its own `apa_web.py` route file. The module side has the analogous problem without the frontend axis: e.g. `rfid`'s variant folder currently has only a config JSON and no module class yet, and there's no way to tell `saviour-config` "this new device type is behaviourally a TTL module with different config" without duplicating a whole `src/modules/variants/<type>/` folder — even where a shared base class (`CameraBase`, per the camera-family unification above) already covers the difference through config alone.

Verified character-for-character equivalent menu output against the old hardcoded arrays before landing it. Every variant now has a `variant.conf` (`NAME`, `DESCRIPTION`, and for controllers `FRONTEND` — read by `build_frontend()`, falling back to `DEVICE_TYPE` when absent, so this is a no-op for all five existing frontends today). **Re-checked the "Blocking prerequisite" section below before touching any of this**: confirmed `get_python_path()`/`configure_service()` are already fully dynamic from `DEVICE_TYPE` (no hardcoding beyond the menus themselves), and that the `--regenerate-service`/`mend.sh` mitigation two paragraphs down already covers the staleness risk for *this* change specifically — menu auto-detection doesn't add any new unit-file drift risk beyond what already exists and already has a documented recovery path. So this shipped without the invariant-launcher prerequisite, and deliberately did **not** touch `ENTRYPOINT`/`CONFIG_FILE` (both still require the launcher work below first) — only `NAME`/`DESCRIPTION`/`FRONTEND`, which don't.

  **Naming: `examples/` → `variants/` — executed 2026-08-13, deliberately without the prerequisite chain below.** `src/controller/examples/` and `src/modules/examples/` are now `src/controller/variants/` and `src/modules/variants/`; `src/controller/config/base_config.json` and `src/modules/config/base_config.json` were flattened to `src/controller/base_config.json`/`src/modules/base_config.json` in the same pass (the single-file `config/` wrapper folders added nothing). "Examples" undersold what's there — per this file's own architecture description these are the concrete, deployed implementations, not sample/reference code. This was a deliberate scope decision, not an oversight: the "Blocking prerequisite" and "Required before the folder rename ships, in order" notes below describe a safer sequence (fixed launcher + CWD-relative config fix + invariant unit file, *then* rename) that was consciously skipped in favour of shipping the rename now and mitigating the fallout — see those two notes for what actually happened instead. The manifest work below (`variant.conf`) remains entirely unbuilt; this was the naming change only.

  **Proposed fix — a small per-folder manifest, `variant.conf`.** Flat `KEY=value`, matching the parsing convention `read_config_value()` already uses elsewhere in `saviour-config` (no new `jq`/JSON dependency — the codebase doesn't otherwise pull one in, and none of setup.sh/saviour-config currently do JSON parsing in bash):
  ```
  # src/controller/variants/apa/variant.conf
  NAME="Active Place Avoidance"
  DESCRIPTION="Place avoidance arena with shock-zone tracking"
  FRONTEND="apa"                            # optional, defaults to this folder's own slug
  ENTRYPOINT="apa_controller.py"            # optional, defaults to <slug>_controller.py
  CONFIG_FILE="apa_controller_config.json"  # optional, defaults to <slug>_controller_config.json
  AUTHOR="Andrew Scott-George"              # free-form; saviour-config doesn't need it, but it's a natural place to record who to ask about a rig-specific variant
  ```
  with the module-side equivalent at `src/modules/variants/<slug>/variant.conf` (same shape, minus `FRONTEND`, since modules have no frontend axis).

  - `select_controller_type()` / `select_module_type()` build their whiptail `--menu` args by globbing `*/variant.conf` and reading `NAME`/`DESCRIPTION`, instead of a hardcoded array — adding a variant becomes "add a folder + manifest," never a `saviour-config` code change.
  - `get_python_path()` and `build_frontend()` read `ENTRYPOINT`/`FRONTEND` from the manifest when present, falling back to today's `<slug>_<role>.py` / `VITE_VARIANT=<slug>` convention when absent — every *existing* type therefore needs only a two-line manifest (`NAME`, `DESCRIPTION`) to keep working exactly as now, fully backward compatible, zero Python or Vite changes required to migrate.
  - This is what actually unlocks "new frontend, no new controller class": a hypothetical new variant's manifest sets `FRONTEND="gridtask"` and `ENTRYPOINT="../basic/basic_controller.py"`, reusing `BasicController` wholesale instead of generating another no-op subclass like `loom_controller.py`.
  - **The catch, and the part of this most likely to be underestimated**: `BasicController.__init__` currently hardcodes `self.config.load_controller_config("basic_controller_config.json")` — the config filename lives *inside* the Python class body, not just the folder-naming convention. Reusing `basic_controller.py` for a second variant means it would still load `basic_controller_config.json`, not the new variant's own config. Closing this means threading the config filename in at construction time (from the manifest's `CONFIG_FILE`, via a CLI arg or env var set in `saviour.service`'s `ExecStart`) rather than each subclass's `__init__` hardcoding its own filename string — a change to `Controller.__init__`/`Module.__init__` made once, not once per subclass, but touching every existing controller and module class's constructor signature.

  **Blocking prerequisite, found 2026-08-01 — accepted and shipped anyway 2026-08-13.** `configure_service()` in `saviour-config` bakes `WorkingDirectory=${DIR}/${PYTHON_PATH}` and `ExecStart=${DIR}/env/bin/python ${PYTHON_FILE}` as literal text into `/etc/systemd/system/saviour.service`, generated once whenever `saviour-config` runs. `update_saviour()` (`module.py`) — the fleet code-update path — `rsync`s new code over the install directory and then just `systemctl restart saviour.service`; it never regenerates the unit file. So an already-deployed device's unit file keeps pointing at the old `src/controller/examples/<type>/` path after an update lands new code at `src/controller/variants/<type>/` — the service fails to start, and stays down until something regenerates the unit file. This is not specific to this rename: **any** future change to `PYTHON_PATH`/`PYTHON_FILE` — including the manifest's own `ENTRYPOINT` override once it exists — has the same latent bug; the rename was just the first change that would actually trigger it.

  **Mitigation shipped instead of the full prerequisite chain**: `saviour-config --regenerate-service` (new) reads the device's current `/etc/saviour/config` and rewrites `saviour.service` via the same `configure_service()` used by the interactive flow, without restarting it or touching role/type. `mend.sh` step 7 now calls this on every run before deciding whether to restart the service — so `sudo bash mend.sh` alone recovers a device whose unit file drifted, without a full interactive `sudo saviour-config` session. **This is a stopgap, not the structural fix**: it only helps a device someone actually re-runs `mend.sh` (or `saviour-config`) on. A device that's merely `update_saviour()`-updated and left alone — the normal fleet code-push path — still has a stale unit file and stays down until mended. The invariant-launcher design in the next two notes is what actually closes this permanently; it remains undone.

  **Revised fix (2026-08-01, supersedes an earlier draft of this note that proposed just regenerating the unit file on every update): make the unit file invariant instead of regenerating it.** Rather than patching the update path to keep a per-variant unit file in sync, remove the need for it to ever change. `saviour.service` should always run one fixed entrypoint — e.g. `WorkingDirectory=${DIR}` / `ExecStart=${DIR}/env/bin/python src/main.py` — regardless of `DEVICE_TYPE`/`DEVICE_ROLE`. That launcher reads `DEVICE_TYPE`/`DEVICE_ROLE` from `/etc/saviour/config` (already the source of truth `saviour-config` writes to today), resolves the matching `variants/<slug>/variant.conf`, and dynamically imports and runs whatever `ENTRYPOINT` class it names. `configure_service()` then writes the *same* unit file contents no matter what type/role is selected — `rsync`-ing new code during an update just changes what the fixed launcher's next start resolves to, the same way any other Python change ships today. This closes the whole class of bug (unit file drifts from repo state) rather than this one instance of it, and it means a future `ENTRYPOINT` override needs zero systemd-side work at all.

  **The catch this design surfaces**: `load_controller_config()` / `load_module_config()` (`src/controller/config.py:99`, `src/modules/config.py:105`) resolve their config-filename argument with `os.path.abspath(...)` — i.e. relative to the process's **current working directory**. That only works today because `WorkingDirectory` happens to be set to each variant's own folder. Under a fixed, invariant `WorkingDirectory`, every existing `<Type>Controller.__init__`'s `self.config.load_controller_config("<type>_controller_config.json")` call would resolve against the wrong directory — and fail *silently*: `load_controller_config`/`load_module_config` just log a warning and return if the path doesn't exist, they don't raise, so a controller would quietly boot with an empty/default config rather than crash loudly. `loom_camera_module.py:499` already shows the right pattern for this — it resolves its ROI JSON via `Path(__file__).resolve().parent`, not CWD. Adopting the fixed-launcher design means every config-loading call needs the same treatment: resolve against the variant's own file location (or have the launcher pass an absolute path in), not against CWD. This touches every existing controller/module `__init__` the same way the `CONFIG_FILE`-injection catch above does — worth doing as the same pass of work, not two separate migrations.

  **This safer order was not followed.** The original plan was: (1) fixed launcher (`src/main.py` or similar) + dynamic dispatch from `/etc/saviour/config` and `variant.conf`'s `ENTRYPOINT`; (2) config-loading calls switched from CWD-relative to `__file__`-relative or launcher-supplied absolute paths; (3) `configure_service()` updated to write the one invariant unit file; only then (4) the `examples/` → `variants/` rename itself, which at that point would have been a pure content move with no systemd-side risk left. Steps (1)-(3) remain fully open — this is still the real fix, and doing it now only has to touch the rename's fallout (the mend.sh mitigation above) rather than also redoing the rename.

  **Does the frontend have to stay physically separate from `variants/`, in `src/controller/frontend/src/<slug>/`?** (question raised 2026-08-01) Not for technical reasons — `vite.config.js` already resolves `virtual:active-app` via a bare `path.resolve()` to an arbitrary path, so nothing stops pointing it at `src/controller/variants/<slug>/frontend/App.jsx` instead. But full colocation is a worse idea than it first looks, for a reason that only shows up by reading the actual imports: `apa/App.jsx` and `habitat/App.jsx` don't just use `basic` as "the default variant" — they import `Sidebar`, and the `Recording`/`Settings`/`System`/`Debug`/`Guide` pages, straight out of `../basic/components/` and `../basic/pages/`. `basic` is simultaneously a variant *and* the de facto shared component library every other variant is built on. Moving `basic`'s frontend under `variants/basic/frontend/` would mean the shared library lives inside one specific variant's own folder — a layering inversion, and it would turn every other variant's `../basic/...` import into a reach across two now-unrelated top-level trees (`variants/apa/frontend/` → `../../../frontend/src/basic/...` or similar), which is worse than what exists today, not better. Keeping one Vite package rooted at `src/controller/frontend/` (one `package.json`, one `node_modules`, one lint config) is also just normal JS tooling hygiene that scattering source across `variants/*/frontend/` would fight.
  Recommendation: don't colocate. The manifest's `FRONTEND=<slug>` field is already the explicit, greppable link between a controller variant and its frontend — arguably better than physical proximity, since the relationship isn't 1:1 anyway (multiple controller variants could share one frontend, or vice versa). If the goal is really "make the shared component library not feel like it's hiding inside a variant," the actual fix is a separate, smaller cleanup: extract the genuinely-shared pieces of `basic/components` and `basic/pages` into a neutral `src/controller/frontend/src/shared/`, so `basic` stops being special and other variants import from `../shared/...` instead of `../basic/...`. That's worth doing independently of this refactor, and would need to happen before colocation could ever make sense.

  **Migration cost**: mechanical for existing types — one small manifest file per existing folder (5 controller + ~8 module folders), no behaviour change since every field defaults to the current convention when absent. The `CONFIG_FILE`-injection piece is the only part that touches existing class code, and is a one-time change to the two base classes rather than per-subclass work. **Actual scope of the `examples/` → `variants/` rename itself (2026-08-13), corrected from the original estimate above**: `saviour-config`'s `get_python_path()` was the only *generated* path string, but the actual diff also touched every hardcoded `examples/` reference that had accumulated — `loom_camera_module.py`/`loom_stimulus.py`'s cross-module imports and hardcoded ROI/texture asset paths, five test files' imports, `tools/convert_to_hailo.py`'s default model paths, and prose paths in `docs/Overview.md`, `docs/CONFIG_STRUCTURE.md`, `docs/remote_samba_setup.md`, `docs/readthedocs/about/contributing.md`, and three deployment scripts (`clone_prep.sh`, `push_credentials.sh`, `uninstall.sh`). None of that was itself risky (grep-and-replace, verified with a full repo-wide sweep afterward) — it just means "touches `get_python_path()` and nothing else" undersold the real footprint of a folder rename in a codebase with several years of hardcoded paths accreted around it.

It has an `auto` grid layout for an arbitrary camera count plus a named `loom` preset (LoomCam large-left / Home top-right / ScreenCam bottom-right) matching the loom rig's actual 3-camera set. Not yet wired into `web.py` — no Flask route, no frontend layout picker, no job queue/progress reporting for a render that could take a while on a Pi. Next steps if this gets picked up: (1) a POST endpoint that takes a layout spec and kicks off a background render (reuse the `export_queue.py`/threaded-job patterns already in this codebase rather than blocking a request); (2) a minimal frontend layout picker (even a fixed set of named presets to start, rather than full drag-resize); (3) generalize `_loom_regions`'s named-preset approach into something manifest-driven once there's a second real preset to justify it, rather than guessing the right abstraction from one example.
  - **Audio/spectrogram overlay** — not reusable from existing code despite appearances. `src/modules/variants/microphone/microphone_module.py` already renders a spectrogram, but only live (cv2+numpy FFT, MJPEG monitoring stream during recording) — turning that into a post-hoc renderer from a saved audio file is new work, not a wire-up.
  - **TTL/event timeseries plot** — genuinely from zero. No charting library exists anywhere in the frontend (`package.json` has no Chart.js/Plotly/D3/recharts); picking one and building a first timeseries component is its own small design decision, independent of the video work.
  Recommendation if this moves forward: ship video-layout compositing as its own PR first (it already has a working prototype and reuses nothing speculative), then treat spectrogram overlay and TTL charting as separate follow-on PRs — bundling all three into one v1 risks stalling on the two components that don't have a head start.

- [ ] **Direct-from-module recording download, as a fallback when export fails** (proposed 2026-08-17, not yet implemented) — the export-confirmation work above (`pending_exports`/`_check_export_stall_after_stop()`) can now tell an operator that a session's files never made it to the controller's Samba share, but today gives them no recovery path beyond SSH'ing into the module and pulling `/var/lib/saviour/recordings` by hand. Idea: a "download all" straight from the module itself, bypassing the Samba export path entirely, for exactly the case where that path is what's broken.
  - **Feasible with existing infrastructure, not a new transport.** `camera`, `microphone`, and `ttl` modules already run `MJPEGStreamServer` (`src/modules/mjpeg_stream.py`) — a small per-module Flask server for their live monitoring view — and the frontend already talks to it directly at `http://{module_ip}:{monitor_port}/...` with no controller proxy (that's how `/video_feed` and the crop-editor's `/snapshot.jpg` work today, per `CameraBase.register_routes()`). A `/download_recordings` route added the same way, zipping `self.facade.get_recording_folder()` and streaming it back, is a small change reusing that exact pattern — same shape as the controller's existing per-session "Download all" button.
  - **Coverage gap**: `apa_arduino`, and any future `rfid`/`sound` module, don't run that Flask server at all today (no monitoring stream need) — they'd get nothing from this unless a minimal always-on HTTP server were added to the base `Module` class instead of bolting onto the existing monitor server. Starting with camera/microphone/ttl (the types that already have the server, and also the types producing the large files where export failure actually matters) avoids that bigger change.
  - **Auth is the real open question.** Like the existing MJPEG stream, this would most naturally be unauthenticated — anyone on the LAN who can reach the module's IP could pull its raw recordings without ever touching the web UI's login. That matches this codebase's existing closed-LAN posture for streaming (see the Security section above), but it's a step up in stakes: raw research data rather than a live camera view. Whether that's acceptable as-is, or whether this should sit behind some form of gate the plain MJPEG stream doesn't have, is a call for whoever picks this up — deliberately left open rather than guessed at here.
  - Explicitly deprioritised for now per direct instruction — documented so the design/feasibility work isn't lost, not queued for near-term implementation.

## Hardware gotchas

### AudioMoth USB microphone

- **Device name encodes sample rate.** The AudioMoth firmware names its USB audio device after its current sample rate (e.g. `250kHz AudioMoth USB Microphone`). Calling `configure_audiomoth()` to change the rate causes PulseAudio/PipeWire to drop the old device ID and register a new one. Any code that stores a PulseAudio device ID (e.g. `self.audiomoths`) must re-discover after reconfiguration — otherwise `soundcard.get_microphone(id)` raises `IndexError` intermittently while the monitoring stream (opened at startup) keeps working on the stale stream.
- **Effective bandwidth is much lower than Nyquist at low sample rates.** The EFM32's PDM decimation filter provides only a fraction of the theoretical bandwidth: ~5 kHz usable at 48 kHz, ~20 kHz at 96 kHz, ~70 kHz+ at 192 kHz. 192 kHz is the only rate suitable for ultrasonic rodent vocalisation work. Do not assume Nyquist = usable bandwidth when validating or warning about sample rate choices.
- **Monitoring and recording use separate soundcard recorders** on the same physical device. PipeWire supports multiple simultaneous readers, so this is intentional and works correctly.

### Controller clock (PTP grandmaster)

- The controller runs `phc2sys` to discipline the system clock from its PTP hardware clock. This means `systemd-timesyncd` / NTP is active and `timedatectl set-time` will fail with *"Automatic time synchronization is enabled"*. Any code that sets the system time must disable NTP first (`timedatectl set-ntp false`), set the time, then re-enable it (`timedatectl set-ntp true`) — ideally in a try/finally.

### Hailo AI HAT / PCIe driver (`apa_camera`, `lightning_camera`)

- **`hailort-pcie-driver` needs `dkms` installed *before* it does, or it silently falls back to an unmanaged one-off kernel module build that breaks again on the next kernel upgrade** (found 2026-08-18, diagnosing a Pi where `hailortcli scan`/`fw-control identify` reported no devices found despite `lspci` showing the Hailo chip fine). The driver package's postinst tries to register the module with DKMS; if `dkms` isn't present yet it prints `Failed to install PCIe driver to the DKMS tree. Trying to install PCIe driver without DKMS` and builds a plain module for the *currently running* kernel only — nothing rebuilds it on the next `apt upgrade` that bumps the kernel, so it silently goes missing again (`modprobe hailo_pci` then fails with `Module hailo_pci not found in directory /lib/modules/<new-kernel>`). `configure_module_dependencies()` (`saviour-config`) just did `apt-get install -y hailo-all` with no `dkms` dependency ensured first — fixed by adding `dkms` ahead of `hailo-all` in both `apa_camera`'s and `lightning_camera`'s `variant.conf` `APT_PACKAGES` (order matters: the loop installs packages one at a time in list order, so `dkms` must come first to be present when `hailo-all`'s `hailort-pcie-driver` postinst runs). This only fixes *new* installs — an already-provisioned Pi in this state needs a one-time manual fix: `sudo apt install dkms && sudo apt install --reinstall hailort-pcie-driver && sudo reboot`.
- **Diagnostic order for "Hailo device not found"**: `lspci | grep -i hailo` first (is the PCIe link even up? if not, check `dtparam=pciex1`/`dtparam=pciex1_gen=3` in `/boot/firmware/config.txt`, needs a reboot after adding) → `lsmod | grep hailo` (is the kernel module loaded at all?) → `dmesg | grep -i hailo` (load attempted and failed, or never attempted?) → `dkms status` (built against the running kernel, per `uname -r`, or a stale one?).
- **Hailo-8 vs Hailo-8L**: `lspci | grep -i hailo` also names the actual chip (`Hailo-8 AI Processor` vs a Hailo-8L one) — worth checking before deploying a `.hef`, since `tools/convert_to_hailo.py`'s `--hw-arch` defaults to `hailo8l` (the standard AI Kit chip) but some devices carry the full Hailo-8 (26 TOPS vs 13 TOPS) instead.

### Module offline detection

- Modules do **not** send a graceful mDNS goodbye on ungraceful disconnection (power loss, switch unplug). The heartbeat timeout (90 s, `HEARTBEAT_TIMEOUT_SECS` in `modules.py`) is the only mechanism for detecting these. The `last_heartbeat_time` field on `Module` must be non-zero before the timeout logic fires, so newly registered modules with no heartbeat yet are not immediately evicted.

### Camera framesync (multi-camera timing)

The camera module supports `camera.sync_mode: "server" | "client" | "none"`. This uses **libcamera's software sync mechanism**, not GPIO. The server broadcasts timing packets over UDP; clients adjust their framerate to match. Key facts:

- **`SyncTimer` metadata**: counts down (in µs) to the agreed sync point, then goes negative. A very negative value (e.g. −26 seconds) means sync was established long before recording started — not an error.
- **`SyncReady` metadata**: True on the single frame where synchronisation fires. The encoder's `sync_enable = True` flag discards frames until this fires, then starts recording. `SyncFrames` is set in `_pre_create_first_segment()` to force a fresh sync point close to T=0. The per-frame timestamp CSV is opened in `_start_new_recording()` (not `_pre_create_first_segment()`) so CSV row 0 always corresponds to video frame 0.
- **Phase offset**: Even after sync-lock, there is a fixed per-session inter-camera phase offset (typically 0–8333 µs at 120 fps). This is a hardware characteristic of when the client's frame clock happened to be when sync was established — **not** a PTP error. It is constant within a session and can be calibrated out from the `framesync_per_frame.csv` sidecar.
- **120 fps limitation**: libcamera sync requires the target framerate to be significantly below the camera's maximum so the client can speed up to catch the server. At 120 fps on Pi Camera Module 3 (which maxes at ~120 fps at the recording resolution), the client has no headroom and cannot phase-lock. The `sync_enable` / `SyncFrames` approach is still used (best-effort), with a 2-second fallback timeout.
- **PTP two-servo rule**: `ptp4l` disciplines the PHC; `phc2sys` disciplines `CLOCK_REALTIME`. The PTP gate in `recording.py` checks both `ptp4l_offset` and `phc2sys_offset` (both must be < `ptp_threshold_us`, default 50 µs). `phc2sys_freq` (the frequency correction in ppb) reflects the crystal oscillator's natural offset and is typically 20,000–30,000 ppb on settled hardware — **this is normal and should not be gated on**. What matters is the *difference* between cameras' freq values, not the absolute magnitude. Wait at least 5–10 minutes after a camera reboot before recording for phc2sys to converge its frequency estimate to the correct value for that crystal.
- **Framesync analysis**: `tools/analyse_framesync.py` reads per-session timestamp CSVs and reports inter-camera offset statistics including clock drift (µs/sec) and detrended jitter (the true timing noise floor once slow PTP drift is removed). Run with `source env2/bin/activate` (needs pandas). The "mean offset" includes the fixed phase offset; the **detrended p95** is the meaningful accuracy figure (<20 µs with settling PTP, <5 µs when fully converged).
