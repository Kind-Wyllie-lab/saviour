  - **`src/controller/frontend/src/basic/utils/themes.js`** (new) — `THEME_TOKENS` (the 8 themeable vars: bg / card-bg / text / secondary-text / accent / accent-alt / border / button — `--ready-color`/`--recording-color` stay fixed, semantic), `BUILTIN_THEMES` (**Default** = verbatim `index.css` values so existing installs are pixel-identical; **SIDB**, **UofE** = supplied brand hex; **Wood**, **Kind**, **Pagan** = from supplied Coolors palettes, light mapped from the palette + dark synthesised), `resolveTheme` / `themeTokens` / `listThemes`.   - **`web.py`** — `self.theme_store`; new `_controller_config_payload()` injects `frontend.custom_themes` (from disk) into every `controller_config_response`; `save_controller_config` strips `custom_themes` back out before persisting. ## 2026-09-01

- [x] **Modules boot + report a fault state instead of crashing when their expected sensor hardware is missing** (branch `feat/module-hardware-fault-state`, 2026-09-01; **not merged, not hardware-verified — backend suite green in a scratch venv (942 passed / 1 skipped), `npm run build` not run**) — before this, a camera module with no sensor on the CSI bus **crashed on startup** (`CameraBase.__init__` calls `Picamera2()` unconditionally), so from the controller's side a camera with a dead ribbon cable looked **identical to a powered-off device**. Now the module always boots, registers, and reports *why* it can't record.
  - **New `hardware_fault: str | None` field** on `ModuleHealthSnapshot` (`src/shared/health.py`) — a human-readable reason, or `None` when healthy. Additive/optional. Flows module→controller every heartbeat via `ModuleFacade.get_hardware_fault()` (generic `getattr`) → `Health.get_health()` → snapshot. `System.jsx` renders a red **`NO HARDWARE`** badge (hover = the reason).
  - **`CameraBase.__init__`**: `Picamera2()` + sensor-property reads + `_configure_camera()` wrapped in try/except → on failure sets `self.picam2 = None` and `self.hardware_fault`. Every downstream path that would then `AttributeError` on `None` got a guard (`_check_picam`, `configure_module_special`, `_start_new_recording`, `_start_next_recording_segment`, `start_streaming`). `habitat_camera`'s override got the same guard.
  - **`recording.py` generic gate (also fixes a latent pre-existing bug)**: `_create_initial_recording_segment()` **ignored** `facade.start_new_recording()`'s return value, so `_begin_recording()` **always** declared success. Now it returns `bool` (`result is not False` — strict, because microphone/ttl/sound/template legitimately return `None` on success), and `_begin_recording()` returns `{"result": "error", …}` without marking `is_recording` when it's `False`.
  - **`microphone_module.py`**: `self.hardware_fault` set by `_find_audiomoths()`; new `@check() _check_audiomoths()` re-scans live (AudioMoths are hot-pluggable); `_start_new_recording()` returns `bool` and sends `recording_start_failed` + returns `False` in the zero-mics case.
  - **`basler_camera_module.py`**: `__init__` no longer `raise`s for missing pypylon / no device — sets `hardware_fault`, `camera = None`, guards.
  - **Already correct, not touched**: `rfid` (the reference pattern) and `apa_arduino` (its own exception path).
  - **Not done**: no proactive one-shot "hardware_fault" status push at boot; `ttl` not audited; `npm run build` not run. Tests: `TestCheckPicam` / `TestStartNewRecordingNoHardware` / `TestStartNextRecordingSegmentNoHardware` / `TestStartStreamingNoHardware` / `TestConfigureModuleSpecialNoHardware` in `test_camera_base.py`, `TestStartRecordingModuleReportsFailure` (2) in `test_recording.py`.
