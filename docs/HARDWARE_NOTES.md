## AudioMoth USB microphone

- **Device name encodes sample rate.** The AudioMoth firmware names its USB audio device after its current sample rate (e.g. `250kHz AudioMoth USB Microphone`). Calling `configure_audiomoth()` to change the rate causes PulseAudio/PipeWire to drop the old device ID and register a new one. Any code that stores a PulseAudio device ID (e.g. `self.audiomoths`) must re-discover after reconfiguration — otherwise `soundcard.get_microphone(id)` raises `IndexError` intermittently while the monitoring stream (opened at startup) keeps working on the stale stream.
- **Effective bandwidth is much lower than Nyquist at low sample rates.** The EFM32's PDM decimation filter provides only a fraction of the theoretical bandwidth: ~5 kHz usable at 48 kHz, ~20 kHz at 96 kHz, ~70 kHz+ at 192 kHz. 192 kHz is the only rate suitable for ultrasonic rodent vocalisation work. Do not assume Nyquist = usable bandwidth.
- **Monitoring and recording use separate soundcard recorders** on the same physical device. PipeWire supports multiple simultaneous readers, so this is intentional and works correctly.

## Controller clock (PTP grandmaster)

- The controller runs `phc2sys` to discipline the system clock from its PTP hardware clock. This means `systemd-timesyncd` / NTP is active and `timedatectl set-time` will fail with *"Automatic time synchronization is enabled"*. Any code that sets the system time must disable NTP first (`timedatectl set-ntp false`), set the time, then re-enable it (`timedatectl set-ntp true`) — ideally in a try/finally.

## Hailo AI HAT / PCIe driver (`apa_camera`, `lightning_camera`)

- **`hailort-pcie-driver` needs `dkms` installed *before* it does, or it silently falls back to an unmanaged one-off kernel module build that breaks again on the next kernel upgrade** (found 2026-08-18). If `dkms` isn't present, the postinst prints `Failed to install PCIe driver to the DKMS tree. Trying to install PCIe driver without DKMS` and builds a plain module for the *currently running* kernel only — nothing rebuilds it on the next `apt upgrade`, so `modprobe hailo_pci` then fails with `Module hailo_pci not found`. Fixed for new installs by ordering `dkms` ahead of `hailo-all` in both variants' `variant.conf` `APT_PACKAGES` (the loop installs one at a time in list order). Already-provisioned Pi in this state: `sudo apt install dkms && sudo apt install --reinstall hailort-pcie-driver && sudo reboot`.
- **Diagnostic order for "Hailo device not found"**: `lspci | grep -i hailo` first (is the PCIe link up? if not, check `dtparam=pciex1`/`dtparam=pciex1_gen=3` in `/boot/firmware/config.txt`, reboot after adding) → `lsmod | grep hailo` → `dmesg | grep -i hailo` → `dkms status` (built against the running kernel per `uname -r`?).
- **Hailo-8 vs Hailo-8L**: `lspci | grep -i hailo` names the actual chip. `tools/convert_to_hailo.py`'s `--hw-arch` defaults to `hailo8l` but some devices carry the full Hailo-8 (26 TOPS vs 13). Note `lspci` sometimes says generic "Hailo-8" for a real 8L — confirm via `hailortcli fw-control identify` (`.arch`).

## Pi 5 PoE power delivery (NVMe controllers + PoE HAT modules)

Every device is a Pi 5 powered over PoE — controllers via the 52Pi EP-0240 M.2 NVMe M-Key PoE+ HAT, most modules via the Waveshare "PoE HAT (F)".

- **NVMe autonomous power-state transitions (APST) can wedge the whole device, requiring a manual power cycle** (found 2026-08-25, live on a habitat controller booting from a Kingston SKC3000S512G). Diagnosed from `journalctl -b -1 -k`: bursts of `nvme nvme0: I/O tag ... timeout, aborting req_op:WRITE`; the first two recovered, the third did not — journal goes silent for ~5 h until a manual power cycle (root filesystem hung). Not undervoltage (`vcgencmd get_throttled` was `0x0` the whole boot). Cause: the kernel default `nvme_core.default_ps_max_latency_us` (100 ms) lets the drive drop into a deep power-saving state it can fail to wake from.
  - **Fix**: append `nvme_core.default_ps_max_latency_us=0` to `/boot/firmware/cmdline.txt` and reboot. Applied automatically by `setup.sh`'s `configure_nvme_power_management()` (fresh) and `mend.sh` step 7/9 (deployed), both idempotent, both printing a reboot reminder. NVMe-specific, so controllers only. `multiclone.sh` clones inherit it (it only patches the PARTUUID) as long as the master image has had `setup.sh`/`mend.sh` run since this landed.
- **`PSU_MAX_CURRENT` (bootloader EEPROM) was found completely unset on the same controller** — the Pi 5 bootloader learns a high-amp supply via USB-C PD, which never happens over a GPIO-header PoE HAT, so it defaults to a conservative 3A budget instead of the ~4.5A both HATs can deliver. Both vendors document `PSU_MAX_CURRENT=5000` as a required step. Plausibly a contributing factor to the hang above.
  - **Fix**: `sudo rpi-eeprom-config --apply <config-with-PSU_MAX_CURRENT=5000>`, reboot. Applied automatically **fleet-wide** (not NVMe-gated) by `setup.sh`'s `configure_psu_max_current()` and `mend.sh` step 8/9, both idempotent.
  - **Caveat**: `rpi-eeprom-config --apply <file>` defaults to bundling the *latest available* bootloader firmware release when the file doesn't pin a `.bin` — so applying just this one line can also silently bump the bootloader firmware (same stable channel). Harmless in practice.
  - Like the NVMe fix, `rpi-eeprom-config` reads the *currently running* config — it won't self-report `[OK]` until after the reboot.
- **Module-side reboots have now been seen too** (found 2026-08-27, habitat session `CRLLT3-247Cameras-camera-173650`) — 5 of 16 camera modules each did one unexplained full OS reboot over 19 h (`health.json` `uptime` reset, segment counter restarted). The 2 h journal retention was too short to catch the cause. A `Waveshare PoE HAT (F)` module browning out under sustained encode + hourly concurrent-export load is exactly the `PSU_MAX_CURRENT`-unset scenario — rule it in/out first on the affected Pis (`camera_34ec`, `camera_a2d2`, `camera_d549`, `camera_d586`, `camera_98b7`).
- **Each recording session now exports its own journal snapshot** (2026-08-27, `fix/habitat-session-followups`) — `Recording.stop_recording()` writes `<session>_<module>_journal_(<ts>).txt` (saviour.service + kernel, `--since` the recording start) into `to_export/`, so it rides the normal export to the share next to the footage. Best-effort; toggle with `recording.export_session_journal` (default on).
- **Export Diagnostics bundle now includes previous-boot + kernel journals** (2026-08-27) — was `journalctl -u saviour.service -n 500` per side (current boot, unit only, no kernel), structurally blind to a reboot cause. Now each module returns: `logs.txt` (current boot, 3000 lines), `logs_prevboot.txt` (`-b -1`), `kernel_prevboot.txt` (`-k -b -1`), `boots.txt` (`--list-boots`); the controller adds `kernel.txt`. Depends on persistent journald actually being on.
- **✅ Persistent journald never worked on any Pi — root cause found 2026-09-30 (branch `fix/journal-persistence-and-ptp-flood`).** Raspberry Pi OS ships `/usr/lib/systemd/journald.conf.d/40-rpi-volatile-storage.conf` (`Storage=volatile`); drop-ins override `/etc/systemd/journald.conf`, so the `Storage=persistent` that `setup.sh`/`mend.sh` wrote there was always ignored and every journal was RAM-only (the earlier "cloned from an old master image" diagnosis was wrong — `mend.sh` could not have fixed it). Both now write `/etc/systemd/journald.conf.d/99-saviour.conf` (sorts after `40-rpi-*`) + restart + `journalctl --flush`; `mend.sh` checks the *effective* `Storage=` via `systemd-analyze cat-config`. Verified on the desk module: a reboot now leaves the previous boot readable (`journalctl --list-boots` shows 2). Side effect: boots no longer start with the clock at "Aug 31". Roll out with `run_mend` fleet-wide **before** the next habitat reboot investigation.
- **`mend.sh` reboot marker: `/run/reboot-required`** — written (with a one-line `saviour mend: ...` reason) whenever step 7 (NVMe APST) or step 8 (`PSU_MAX_CURRENT`) *actually changed* something, and `mend.sh` exits `10` instead of `0`. Deliberately the same path Debian's `update-notifier` uses; `/run` is tmpfs so it self-clears on the reboot. `mend.sh --reboot` (opt-in, default off) reboots at the end iff the marker was written; `run_mend(reboot=True)` passes that through and its reply is `{"result": "reboot_required"}` (still a success). Find mended-but-not-rebooted devices: `[ -f /run/reboot-required ]` across the fleet, or exit-10 in `/var/log/saviour-mend.log`.
- **Diagnostic checklist for "Pi went unreachable, needed a power cycle"** on any Pi 5 in this fleet: `journalctl --list-boots` (find the gap and the preceding boot) → `journalctl -b -1 -k -g nvme` (timeout bursts; NVMe only) → `vcgencmd get_throttled` (flagged undervoltage — a live/sticky-since-boot read, not historical) → `sudo rpi-eeprom-config | grep PSU_MAX_CURRENT` (missing/wrong = firmware may have been power-budget-limiting; `[ -f /run/reboot-required ]` = fix queued but not activated) → NVMe devices also: `cat /sys/class/nvme/nvme0/power/control` (`auto` = APST active) and `/sys/module/nvme_core/parameters/default_ps_max_latency_us` (100000 = default/unmitigated).

## Module offline detection

- Modules do **not** send a graceful mDNS goodbye on ungraceful disconnection (power loss, switch unplug). The heartbeat timeout (90 s, `HEARTBEAT_TIMEOUT_SECS` in `modules.py`) is the only mechanism for these. `last_heartbeat_time` must be non-zero before the timeout fires, so newly registered modules with no heartbeat yet are not immediately evicted.

## PTP network topology (multi-switch habitats)

The controller is the PTP grandmaster; every module disciplines its PHC from it. The fleet switches (habitat rigs: **TP-Link TL-SG1218MPE**, 16-port Gigabit PoE+ "Easy Smart") are **plain L2 — not IEEE 1588 transparent or boundary clocks**. That has two consequences `ptp4l` cannot correct for:

- **Every switch hop adds variable queuing (residence) delay** to PTP event messages. A non-PTP switch doesn't measure or subtract it, so it shows up as offset jitter that grows with hop count.
- **Bulk traffic on a shared link delays PTP packets** — a Samba export frame in flight makes the next Sync/Delay_Req wait behind it. `ExportQueue` caps this at `max_concurrent_exports`, but even 1–2 concurrent ~250 MB transfers across the trunk a module syncs over is enough to nudge a marginal slave over threshold.

**This is fixed by wiring, not code.** SAVIOUR must stay topology-agnostic — do not add QoS-tuning, VLAN-aware logic, or per-habitat network assumptions. The standard for any habitat, independent of module count:

1. **Grandmaster (controller) and the export share on the same switch.** That switch is the PTP root.
2. **No module more than 2 switch hops from the controller** (1 is ideal).
3. **No third switch in the PTP path.** With two habitat switches, link them *directly* — SFP-to-SFP — not via an aggregation switch.
4. If a building uplink is needed, hang it off **one** habitat switch as an edge port so grandmaster traffic never traverses it.
5. Beyond 2 switches per habitat, or if contention persists at 2 hops, the answer is **PTP transparent-clock switches**, not config.

**Found 2026-08-27** (habitat session `CRLLT3-247Cameras-camera-173650`): two TL-SG1218MPEs joined *via a third switch* gave far-side modules a 3-hop uncorrected path vs 1 hop for modules on the controller's switch, matching the clean-vs-marginal split (8 stable / 12 unstable, the 12 including all 4 microphones). Remedy: direct SFP link between the two switches, controller + share on one, middle switch demoted to edge-uplink-only. Confirm before/after by mapping module MAC → switch port (each switch's web GUI, Monitoring → MAC address table) against the controller's `ip neigh`, and a fresh `/api/ptp_history.csv` a day after. This was a *secondary* contributor — the primary cause of the hourly sync episodes was the `_check_ptp_health()` restart loop, whose fix is **now merged** (`9d42893f`, `b0191ba1`); re-measure on a 24 h habitat run (roadmap A8) before deciding how much the rewire still buys.

## Camera framesync (multi-camera timing)

The camera module supports `camera.sync_mode: "server" | "client" | "none"` — **libcamera's software sync**, not GPIO. The server broadcasts timing packets over UDP; clients adjust their framerate to match.

> **Open decision (2026-09-07): default `sync_mode` to `none` (free-run)?** The sync *client*'s continuous frame-interval nudging is what makes its encoder drop handed frames (server stays clean) — the cause of the `_StreamCursor` misindexing / client-lags-in-compose problem. Behaviour scoring / ethograms don't need sub-frame cross-camera identity (`video_compose` grid-resamples by `timestamp_ns` to ±½ frame). Recommendation + blocking checks: `plans/multicam-frame-alignment-and-sync-provenance.md` → "Decision to make". Also: the `sync_enable`/`SyncFrames` note below is **stale** — current `camera_base._start_new_recording` deliberately does *not* arm them (joins existing phase state).
> **Decided 2026-10-02: keep framesync on by default** (owner's call), with the systemd watchdog as the backstop for its worst failure. Found live that day: with libcamera 0.5.2, a sync **client** whose server disappears blocks in `RPiController::Sync::process` → `recvfrom()` on the IPA thread, so its capture stops; any `Camera.stop()` then waits on that thread forever, and picamera2 calls it holding the GIL, freezing the whole module process (no heartbeats, logs or commands). The controller's FrameSync reconcile triggers exactly that stop when the server drops out. `WatchdogSec=60` (`src/shared/sd_watchdog.py`) now restarts such a process in ~1 min (thread stacks to the journal via faulthandler); in a session the controller re-arms the module and records the gap. Residual: a server dropping out mid-session costs every client ~1-2 min of video, not just the server. Upstream fix would be a non-blocking/timeout recv in libcamera's rpi.sync.


- **`SyncTimer` metadata**: counts down (µs) to the agreed sync point, then goes negative. A very negative value (e.g. −26 s) means sync was established long before recording started — not an error.
- **`SyncReady` metadata**: True on the single frame where sync fires. The encoder's `sync_enable = True` discards frames until this fires. `SyncFrames` is set in `_pre_create_first_segment()` to force a fresh sync point close to T=0. The per-frame timestamp CSV is opened in `_start_new_recording()` (not `_pre_create_first_segment()`) so CSV row 0 always corresponds to video frame 0.
- **Phase offset**: even after sync-lock, there's a fixed per-session inter-camera phase offset (typically 0–8333 µs at 120 fps). A hardware characteristic of when the client's frame clock happened to be when sync was established — **not** a PTP error. Constant within a session; calibrate out from the `framesync_per_frame.csv` sidecar.
- **120 fps limitation**: libcamera sync requires the target framerate to be significantly below the camera's max so the client can speed up to catch the server. At 120 fps on Pi Camera Module 3 the client has no headroom and cannot phase-lock. `sync_enable`/`SyncFrames` is still used best-effort with a 2 s fallback timeout.
- **PTP two-servo rule**: `ptp4l` disciplines the PHC; `phc2sys` disciplines `CLOCK_REALTIME`. The recording-**start** gate (`_check_ptp_sync` in `recording.py`, every start path) checks both `ptp4l_offset` and `phc2sys_offset` against **`recording.ptp_start_gate_us`** (default **50 µs**, its own key since 2026-08-28 — split off `ptp_threshold_us`, now only the looser mid-recording "degraded" *warning*, ~1 ms). Both keys are on Settings → Thresholds. `phc2sys_freq` (ppb) reflects the crystal's natural offset and is typically 20,000–30,000 ppb on settled hardware — **normal, don't gate on it**. What matters is the *difference* between cameras' freq values. Wait 5–10 min after a camera reboot before recording for phc2sys to converge.
- **Framesync analysis**: `tools/analyse_framesync.py` reads per-session timestamp CSVs and reports inter-camera offset stats including clock drift (µs/sec) and detrended jitter. Run with `source env2/bin/activate` (needs pandas). The "mean offset" includes the fixed phase offset; the **detrended p95** is the meaningful accuracy figure (<20 µs with settling PTP, <5 µs when fully converged).
- **On-Pi CPU/NPU load costs the sync *client* frames** (measured 2026-09-08, `tools/framesync_sweep.py`). Anything sharing the Pi with the H264 encoder — most notably `hailo_camera` preview inference — can make the encoder drop handed frames (CSV row written, no container frame) and jitter the capture cadence. It only bites the sync **client** (the server stayed 0-drop at every setting) and only past a load threshold: at 30 fps, `hailo.infer_every_n=1` (inference every frame) → ~6 capture drops + 1 encoder drop + gap-CV 0.056 per 60 s; `infer_every_n≥2` is indistinguishable from inference off. PTP offset is unaffected (~38 µs throughout) — this is throughput, not timing. Re-check `framesync_report.json` / `analyse_framesync.py` after any change to a camera's fps, sensor mode, `sync_mode`, or (hailo) `model` / `infer_every_n`. `tools/framesync_sweep.py` automates a config sweep via the REST API + SSH. See `plans/multicam-frame-alignment-and-sync-provenance.md` item 3.
