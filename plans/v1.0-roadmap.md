- **Status:** proposed

## The bar (unchanged)

> v1.0 = "safe to run unattended on a closed lab LAN without silent data
> loss or easy compromise" — **not** "hardened for internet exposure".

v1.0 deliberately **excludes**: `web.py` blueprint split, Samba→rsync, the
module god-object composition refactor, ZMQ CURVE, web-UI TLS, SMB3
sealing, `update_saviour` package signing, the ZMQ identity-hijack path,
and every in-flight *feature* branch (REST API, dashboard widgets, Habitat
Session plans, compose/ephys, NWB, telemetry, hailo/basler/lightning
model work). Those are v1.1+. The temptation with that much branch
activity is to let v1.0 slip to absorb it — it should not.

## What changes: make the exit checklist concrete

Today the milestone has exactly one *tracked* blocker (CI gating), which
badly understates the distance to the claim. The "Correctness / data loss"
list **is** the v1.0 work but reads as peers with low-priority observability
cleanup. This roadmap promotes the silent-data-loss subset to named exit
criteria and adds a positive acceptance test.

## D. The positive acceptance test (the definition, made executable)

A ≥72 h **unattended** habitat session (controller + ≥2 real modules), with
three faults induced at random points:

1. a module hard-dropped (power/switch) and later restored;
2. the export share filled past the critical threshold, then freed;
3. a PTP degradation forced on one module (offset driven over the gate).

**Assert, for every one:**

- an operator-visible fault was raised (session badge + `session_events.log`
  + alert/digest), with the *correct distinct reason* (dropout ≠ disk-full ≠
  operator-stop ≠ PTP);
- the session self-healed (stayed ACTIVE, module re-armed) where the fault
  was transient;
- the resulting data is **either complete or its gaps are recorded in
  metadata** — no silent hole.

Passing D exercises A1, A3, A4, A6, C3 and validates the
`unattended-session-posture` + `habitat-session-plans` branches that are
currently "built, not run in a real controller".

## A4 proposal (disk-full auto-stop)

Two changes in `src/modules/recording.py`:

1. **Move the disk check out of the segment-boundary gate.** Today it only
   runs inside `if now - segment_start_time > segment_length`. Add a
   lightweight `shutil.disk_usage` check on every `_monitor_recording_length`
   pass (the loop already runs at 10 Hz; check at most once every ~30 s via a
   timestamp). Threshold stays `recording.local_min_free_pct`; add a second,
   higher "warn" threshold that emits a `recording_health_warning` (reuses
   A1's pipe) before the hard stop, so the operator/digest gets a heads-up
   while there's still time to free space.

2. **Distinct stop reason.** `stop_recording()` currently sends
   `{"type": "recording_stopped", "status": "success", "recording": False}`
   identically for operator and self-protective stops. Add a `reason` field
   (`"operator"` default; `"disk_critical"` from the auto-stop path) and a
   `detail` string (free %, free MB). Controller side: a
   `reason != "operator"` recording-stopped is a **FAULT**, not a clean stop
   — surface it like `report_module_fault` (badge + event log + alert/digest,
   ERROR for a normal session, recorded-but-ACTIVE for an unattended one),
   and record the gap in session metadata. An unattended session should try
   to auto-resume that module once free space recovers past the warn
   threshold (hysteresis), mirroring the Habitat-Session disk-autopause
   logic already on `feat/habitat-session-plans`.

Config: `recording.local_warn_free_pct` (default 15), `recording._disk_check_interval_secs` (default 30). Tests: unit-test the reason plumbing + the boundary-independent check; cover the fault path in `test_recording*.py`.
